Frontier — The New Engineering Disciplines

Why this module exists​

You've shipped a feature that calls an LLM, and it's inconsistent — sometimes right, sometimes vague, occasionally wrong in a way that would embarrass you in a demo. Someone on the team says "try tuning the prompt." Someone else says "it's a context problem, the model doesn't have the right data." A third person says "we need better guardrails around what it's allowed to do." All three might be right, or none of them might be — and without a name for each kind of problem, you end up guessing which one to fix first.

This module gives you that vocabulary. Five practices have emerged around building with LLMs — prompt engineering, context engineering, harness engineering, loop engineering, and eval-driven development — and knowing which one a given problem calls for is the difference between a fix that lands and an afternoon spent tuning the wrong knob.

One honest note before you start: this list is not closed. The field is a few years old and still naming its own practices. What's fixed here is the reasoning — how to tell these disciplines apart and match a real problem to the right one. New practices will get added to this module as the field settles on names for them; the five below are the ones already stable enough to teach.

The analogy: onboarding a capable new engineer with no memory of your systems​

Picture hiring a genuinely capable engineer — strong fundamentals, good judgment — who has never worked at your company before and has no memory of your systems, your runbooks, or your past incidents. Every one of today's five disciplines is really a question about how you set that engineer up to do good work:

  • Prompt engineering is how you word the ticket you hand them. A vague ticket ("fix the slow endpoint") gets a different quality of work than a precise one ("the /orders endpoint p99 latency regressed from 200ms to 900ms after yesterday's deploy — investigate and propose a fix"). Same engineer, same skill, different result, purely from how the request was phrased.
  • Context engineering is what's already on their desk when they sit down: the right runbook, the past incident report, the relevant code file — versus an empty desk and a closed door. Even a perfectly worded ticket fails if the engineer doesn't have the information needed to act on it.
  • Harness engineering is which systems they're allowed to touch, what commands are pre-approved, and what format their report has to follow so it plugs into your process. It's the guardrails that stop a well-meaning engineer from rm -rf-ing production, and the structure that makes their output usable by the next step in your pipeline.
  • Loop engineering is how you structure work that takes more than one sitting: when they check in, when they escalate instead of guessing, how progress carries from day one to day two, and how you know the project is actually done versus still needs another pass.
  • Eval-driven development is how you know whether this new hire is actually good at the job — not your gut feeling after reading one report, but a scorecard run across many past incidents, the same way you'd trust a test suite over "it looked fine to me."

Keep this analogy in mind as you read the technical definitions below — each one is answering a version of "how do I set this engineer up to succeed," just applied to a model instead of a person.

Prompt engineering — how you word the single call​

Definition: shaping the wording, structure, and instructions inside one call to the model — the phrasing, the examples you give it, the output format you request, the role you ask it to play.

When it applies: the model already has every fact it needs to answer well, but the way you're asking is producing inconsistent, vague, or wrongly formatted output. A support-bot prompt that just says "answer the customer's question" will drift in tone and completeness call to call; adding a clear structure ("respond in three sentences: acknowledge, answer, next step") often fixes the inconsistency without changing anything else about the system.

What it is not: prompt engineering can't fix a model that's missing information. No amount of clever wording gets a correct answer out of a model that was never given the fact it needs — that gap belongs to the next discipline.

Context engineering — what the model sees, not how you phrase it​

Definition: deciding what information surrounds the model at call time — retrieved documents, conversation history, tool outputs, system state — and how much of it fits inside the context window without crowding out what matters.

When it applies: the model would answer correctly if it had the right facts in front of it, but it currently doesn't, or it has so much irrelevant material stuffed into the call that the signal gets lost. This is the discipline behind RAG design (deciding what to retrieve and how to chunk it), conversation memory (deciding what history to carry forward versus drop), and context budgeting (deciding what earns a place in a limited window). A support bot that "forgets" an earlier detail in a long conversation almost always has a context engineering problem, not a model problem — the detail scrolled out of what the call actually sends.

Harness engineering — the software wrapped around the call​

Definition: the surrounding system that makes a model call safe and useful in production — tool definitions, input/output validation, retries, permission boundaries, sandboxing, and parsing of whatever the model returns into something the rest of your system can use.

When it applies: the model reasons fine in isolation, but the system around it doesn't give it the right tools, doesn't validate what it's allowed to do, or doesn't handle malformed output gracefully. An agent that occasionally calls a tool with the wrong argument types, or one that technically could delete a production record because nothing stopped it, has a harness problem — the fix lives in the code wrapped around the model, not in the prompt.

Loop engineering — orchestrating work across multiple steps​

Definition: how a system structures work that takes more than one model call — how many iterations it runs, when it decides to stop, how state and goals carry from one step to the next, and how a task gets decomposed and re-planned as new information comes in.

When it applies: a single call genuinely isn't enough — the task needs multiple rounds of reasoning, tool use, or self-correction. The characteristic failure modes are different from the other disciplines too: an agent that loops forever refining an answer nobody asked it to refine, one that gives up after one attempt when persistence was called for, or one that loses track of the original goal three steps into a plan. Fixing those is a loop engineering problem — you're redesigning the orchestration, not the wording of any single call.

Eval-driven development — how you know a change actually helped​

Definition: running a change (a prompt tweak, a new tool, a different model) against a representative, repeatable set of real inputs and scoring the output against a rubric — before deciding whether the change ships.

Why it's replacing "just look at it": with deterministic code, a unit test tells you definitively whether a function is correct. An LLM call doesn't have that kind of ground truth — the same prompt can produce a slightly different answer twice, and "it looked better to me on this one example" doesn't tell you what happened to the other thousand questions your system handles. Evals are the practice that closes that gap: a fixed set of representative questions, a rubric or scoring function, and a pass rate you track over time. When a team reports "the new system prompt moved our eval pass rate from 81% to 94%," that number — not a demo, not a feeling — is what earns the change a place in production. Evals are becoming to LLM systems what test suites are to traditional code: the thing you run before you trust a change.

Where these five sit in the build lifecycle​

The five disciplines aren't alternatives you pick between once — they stack as a system grows from a single call into a running agent, and evals sit across all of them as the thing that tells you whether any layer actually improved.

Read it left to right: the simplest system is one call, governed by prompt engineering alone. Add retrieval or injected data and you've added a context engineering problem. Add tools the model can invoke and you've added a harness engineering problem — now something can go wrong in the world, not just in the text. Add multiple steps over time and you've added a loop engineering problem. Evals don't belong to any one stage — they're how you measure whether a change at any stage made the system better or worse.

Matching a real problem to a discipline​

The skill this module is actually teaching is diagnosis: given a real, messy situation, which of the five explains it — and which fixes it. A few worked examples:

  • "Our summaries are inconsistent in length and tone." The model has the input it needs; the request just doesn't constrain the output enough. Prompt engineering.
  • "The assistant keeps citing outdated pricing." The model is answering fluently from memory instead of from the current price sheet it should have been given. Context engineering.
  • "The agent occasionally tries to call a tool that doesn't exist." The wording of the request is fine — the problem is in what tools were registered and how malformed calls are validated before they reach anything real. Harness engineering.
  • "The agent keeps re-researching the same sub-question and never finishes." Every individual call the agent makes is reasonable; the orchestration around when to stop and how state carries forward is broken. Loop engineering.
  • "We changed the system prompt and it feels better, but we're not sure." "Feels better" on one or two examples isn't evidence. Eval-driven development.

You'll work through six more scenarios like these in the lab — this time without the answer handed to you first.

This is a living lesson

These five disciplines are the ones stable enough to name today. As practitioners converge on names for new practices — this field moves fast — later revisions of this module will add them here rather than starting a new module. Treat the taxonomy as current, not final.
