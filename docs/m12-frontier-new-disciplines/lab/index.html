Lab — Diagnose the Discipline

Goal: Prove you can take a real, messy situation and name which of the five disciplines from the lesson explains it — the same diagnostic move you'll make the next time an AI feature at work is misbehaving and someone asks "so what do we actually fix here?"

Time: ~15 minutes Prerequisites: none — this lab is reading and reasoning, not code. If you haven't cloned the labs repo yet, see setup/environment first.

Step 1 — Match 6 real situations to the right discipline​

From the root of the course repo, open the matching exercise:

cd labs/m12
cat discipline-match.md

You'll find 6 short, real-world-style situations — a support bot with inconsistent tone, an assistant citing outdated policy, an agent with a broken tool call, a research agent that can't decide when it's done, a prompt change shipped on gut feeling, and a coding assistant with no way to check its own work. Each one maps to exactly one of the five disciplines from the lesson: prompt engineering, context engineering, harness engineering, loop engineering, eval-driven development.

Work through all 6 before you look at the answer key. Two of them (Scenarios 3 and 6) both land on harness engineering for different reasons — that repetition is deliberate, because harness problems are the ones most often mistaken for prompt problems in real teams.

Once you've written down your 6 answers, scroll to the Answer key section at the bottom of the same file and check yourself against the reasoning, not just the label — the "why" is what you'll actually reuse the next time you're looking at a live system instead of a scenario on a page.

Common Pitfalls​

Reaching for prompt engineering as the default fix

It's tempting to treat every AI misbehavior as "the prompt needs work," because it's the fastest thing to try. Scenarios 2, 3, and 6 are all designed to look like they could be prompt problems on first read — but no amount of rewording fixes a model that's missing information (context), a system that doesn't validate what a tool call does (harness), or an agent that can't check its own output (also harness). Diagnose before you tune.

Confusing "the agent used a tool" with "harness engineering only matters for agents"

Harness engineering isn't just about tools — it also covers output validation, retries, and permission boundaries for any model call, agentic or not. A single-call system that occasionally returns malformed JSON and crashes the caller has a harness problem too, even with no tools and no loop involved.

Treating "it looked better on the examples I tried" as evidence

Scenario 5 is the most common failure in real teams: a change looks like an improvement on the handful of cases someone happened to try, then quietly regresses a category nobody checked. That gap is exactly what eval-driven development closes — a fixed, repeatable, representative test set beats a good feeling every time.

Teardown​

Nothing to tear down here — no processes, no environments, no cloud resources. This lab reads a plain text file and asks you to reason about it.
