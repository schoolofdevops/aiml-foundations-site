Lab — Build Your First AI Agent

Goal: Build a real agent with two tools — web search and a calculator — that researches and summarizes AI news, reasoning step by step in front of you. Then, if you want to go further, give it memory over a PDF with a small RAG pipeline.

Time: ~30 minutes (Lab 4) + ~15 minutes (Lab 5, bonus) Prerequisites: Module 1's lab, completed at least once, and ideally a Google Gemini free-tier key from Module 1 Step 3 Option B — see Step 2 below for why this lab needs it more than earlier ones did.

Step 2 — Configure a provider that actually calls tools reliably​

This step matters more here than it did in Modules 1 and 5. Small local models call tools unreliably — this is a real, known limitation, not something wrong with your setup. A 1.5-billion-parameter model like qwen2.5:1.5b will sometimes skip calling a tool it clearly needs, or answer as if it had called one when it didn't.

Recommended for this lab: Google Gemini's free tier. If you already set up Option B in Module 1, reuse it in this new terminal:

source ../m1/.env

If you skipped Option B in Module 1, set it up now — grab a free key at aistudio.google.com/apikey, then:

cp ../m1/.env.example .env

Open .env, uncomment the Option B — Google Gemini block, paste your key in, save, then load it:

source .env
Ollama is documented, not recommended, for this specific lab

You can point this lab at local Ollama the same way Module 1 did — agent.py defaults to http://localhost:11434/v1 with qwen2.5:1.5b if you set nothing. It will run. It will also, quite plausibly, answer your research task without ever calling web_search, or claim it used the calculator when it didn't. If that happens, that's the model, not a bug in agent.py — switch to Gemini for a reliable demo of the loop actually working. The code in agent.py doesn't change either way; only the three environment variables do.

Step 3 — Look at the two tools before you run anything​

Open tools.py before running the agent — you want to know what it's allowed to do before you watch it decide when to do it.

cat tools.py
ToolWhat it doesWhy it's built this way
web_search(query, max_results)Searches the public web via the ddgs package and returns titles, snippets, and URLsddgs is the current, maintained package for this — the older duckduckgo-search package was frozen upstream and renamed. No API key, no signup, genuinely free
calculator(expression)Evaluates a basic arithmetic expression and returns the resultParses the expression with Python's ast module and only ever walks numbers and + - * / % ** — never Python's built-in eval() on model-provided text

That second row is worth sitting with for a second. A model's tool arguments are text the model generated — not text you typed. Handing that text straight to eval() would let anything the model writes run as real Python on your machine, including instructions an attacker smuggled into a search result the model read earlier (the lesson's prompt injection risk, made concrete). calculator() in tools.py never calls eval(). Confirm it yourself:

grep -n "ast.parse" tools.py

Expected output

63:        parsed = ast.parse(expression, mode="eval").body

You should see ast.parse(expression, mode="eval").body — a call that only ever builds a syntax tree, never runs code. That's the only place the word eval appears anywhere in tools.py as real, executable code — it also shows up twice in comments warning against using it. Search for a bare eval( yourself and you'll find only those two comments and this ast.parse call, never something that looks like eval(some_string) actually running.

Each tool also has a JSON schema right below it in the same file: a name, a description, and the shape of its arguments. That schema is the only thing the model ever sees — it never sees your Python source.

Step 4 — Run the agent, and watch it reason​

This is the moment Module 1 promised you. Run it:

python3 agent.py

Expected output (a real, live agent run, captured against Gemini — tool-call order, arguments, search results, and the final answer will all be different on your own run, since web search results and even today's actual AI news change; here's the shape of what you should see)

Task: Research the top 3 AI news stories from the last few days. For each one, give a one-sentence summary and note where you found it. Then use the calculator tool to work out what percentage 3 is of 10, just to prove you can use both tools, and mention that number at the end.

  -> calling web_search({'max_results': 3, 'query': 'top AI news last few days'})
     result: 1. AI News — Today's Top Stories, Tracked & Ranked | AI Weekly — AI news delivered 3x/week. Curated AI updates on funding, models, regulation, and applications. Read by 50,000+ professionals since 201
  -> calling calculator({'expression': '(3 / 10) * 100'})
     result: 30.0

Final answer:
Here are the top three AI news stories from the last few days:

1.  AI Weekly provides a curated briefing of AI news covering funding, models, regulation, and applications (found on AI Weekly).
2.  Google News features a story about building AI agents with Google Gemini 3 and open-source frameworks (found on Google News).
3.  TechCrunch reports on a writer introducing a new AI model and an upgraded harness to manage token costs (found on TechCrunch).

3 is 30.0% of 10.

Read the printed trace, not just the final answer. Every -> calling ... line is the agent loop from the lesson, made visible: the model decided it needed something, your code ran the tool, and the result — printed right below — went back into the conversation before the model reasoned again. Open the file and see how little code that trace actually took:

cat agent.py
What's new vs. Module 5's qa_cli.pyWhy
tools=TOOLS on chat.completions.create(...)Hands the model the two schemas from tools.py — without this parameter, the model has no tools to call at all
if not message.tool_calls: return message.contentThe exact fork Module 1's deep dive previewed — message.content means answer, message.tool_calls means act
The for _ in range(MAX_ITERATIONS): loopThe reason -> act -> observe -> repeat loop from the lesson's diagram, as real code, with a hard stop

Step 5 — Give it a task of your own​

python3 agent.py "Search for the current price of Bitcoin in USD, then calculate what 15% of that price is."

Expected output (a real run, captured against Gemini — will differ every time, both because of live search results and because the price itself changes; do not expect the dollar figure below to match what you see)

Task: Search for the current price of Bitcoin in USD, then calculate what 15% of that price is.

  -> calling web_search({'query': 'current price of Bitcoin in USD'})
     result: 1. Bitcoin price today, BTC to USD live price, marketcap and ... — The live Bitcoin price today is $63,410.92 USD with a 24-hour trading volume of $19,116,128,927.84 USD. We update our BTC to USD pric
  -> calling calculator({'expression': '63410.92 * 0.15'})
     result: 9511.637999999999

Final answer:
15% of the current price of Bitcoin is approximately $9,511.64.

This task needs both tools in a specific order — search first, since the calculator has nothing to work with until it has a real number — which is a good way to confirm your agent is actually reasoning about sequence, not just calling tools at random.

Lab 5 (bonus) — Simple RAG: give your agent memory​

Everything above is the required lab. This part is optional — a genuine, working extension, not required to complete the module. Module 5 introduced the RAG pipeline conceptually: chunk, embed, retrieve, stuff, generate. Here it is, running against a real PDF.

A small sample document is already in this folder — sample-handbook.pdf, a fictional company's employee handbook excerpt. You can also point the scripts at any small PDF of your own.

Embeddings default to local Ollama (nomic-embed-text), regardless of which provider you configured for agent.py above — embedding and chat generation don't have to be the same provider. Pull the embedding model if you haven't already:

ollama pull nomic-embed-text

Expected output (instant if you already have the model, as here — a fresh pull shows progress bars for each layer first)

pulling manifest
pulling 970aa74c0a90: 100% ▕██████████████████▏ 274 MB
pulling c71d239df917: 100% ▕██████████████████▏  11 KB
pulling ce4a164fc046: 100% ▕██████████████████▏   17 B
pulling 31df23ea7daa: 100% ▕██████████████████▏  420 B

success

Now ingest the PDF — chunk it, embed each chunk, store it in a local Chroma collection:

python3 rag_ingest.py

Expected output (chunk count depends only on the PDF's text length, so this exact count will repeat on any machine ingesting the same sample-handbook.pdf)

Loading sample-handbook.pdf ...
Extracted 1794 characters of text.
Split into 5 chunks.
Embedding 5 chunks with nomic-embed-text (this calls the embeddings endpoint once per chunk) ...
Stored 5 chunks in Chroma at ./chroma_db/ (collection 'm6_rag_demo').
Now run: python3 rag_query.py "your question about the document"

rag_ingest.py split the document into overlapping ~500-character chunks (a whole document embedded as one vector would blur every fact in it together — Module 5's point, now running), embedded each one, and wrote them to chroma_db/ on disk. Nothing gets sent to a chat model in this step — embedding and generation are two different calls.

Now query it:

python3 rag_query.py "How many vacation days do employees get per year?"

Expected output (a real, live run — the chat model's exact phrasing may differ slightly on your run, but the number and the retrieved chunks should not, since they come from the same PDF and the same embedding model)

Retrieved chunks:
  1. mployees accrue 22 days of paid vacation per year, credited monthly at a rate of a little under 2 days per month. Unused...
  2. tion hours, which are 10:00 to 14:00 in the team's primary timezone. 2. Expense Reimbursement Employees working remotely...
  3. ment remains company property and must be returned within 14 days of an employee's last working day, unless a buyout is ...

Grounded answer:
Full-time employees accrue 22 days of paid vacation per year.

rag_query.py embeds your question with the same embedding model, asks Chroma for the three closest chunks by vector distance, pastes them into the prompt, and asks your configured chat model to answer from that context only. Try a question the document doesn't answer:

python3 rag_query.py "What is the company's parental leave policy?"

Expected output (a real, live run — exact wording may vary, but it should decline to answer rather than invent a policy)

Retrieved chunks:
  1. Nimbus Cloud Storage -- Employee Handbook Excerpt 1. Remote Work Policy Nimbus Cloud Storage is a remote-first company. ...
  2. mployees accrue 22 days of paid vacation per year, credited monthly at a rate of a little under 2 days per month. Unused...
  3. tion hours, which are 10:00 to 14:00 in the team's primary timezone. 2. Expense Reimbursement Employees working remotely...

Grounded answer:
I don't know. The provided context does not contain information about the company's parental leave policy.

A grounded answer should tell you it doesn't know, rather than guessing — that's the system prompt in rag_query.py doing its job, and it's the whole reason RAG beats asking the base model directly for anything you need it to get right from your own documents.

Common Pitfalls​

Never call raw eval() on model-generated text

This is worth repeating outside Step 3 because it's the single most important security habit in this lab, not just a code-review nit. If you ever extend calculator() or write your own tool that evaluates model-provided text, run it through ast.parse() and a node-by-node allowlist the way tools.py does — never eval() or exec() directly. Model-provided text should be treated the same way you'd treat text from an anonymous internet user, because in an agent with tools like web search, some of it effectively is.

The agent never calls a tool, or claims it did without a trace line for it

You're most likely on the Ollama path from Step 2 with a small local model. This is the documented reliability gap, not a bug — switch to the Gemini path and re-run before assuming your code is wrong.

json.decoder.JSONDecodeError printed inline, not a crash

Occasionally a model writes malformed JSON in its tool-call arguments. agent.py catches this specifically — you'll see a called with malformed JSON arguments line instead of a stack trace, and the loop continues with an error message fed back to the model instead of your terminal crashing. If you never see this, that's fine — it's a rare failure mode this lab defends against, not one it needs to trigger.

The script prints the max-iterations message instead of an answer

agent.py caps the loop at MAX_ITERATIONS = 8 specifically so a model that keeps calling tools without ever committing to an answer can't loop forever, burning API calls on your key. Seeing the cap message once in a while on a genuinely hard task is expected. Seeing it on every run is a sign the model isn't converging — try rephrasing the task more narrowly, or switch providers.

web_search returns "No search results found" or an error

Live search, run from a shared or rate-limited network, will occasionally return nothing or fail outright — ddgs has no API key or quota to fall back on when DuckDuckGo itself rate-limits a run of requests. web_search() returns a plain error string instead of crashing, so the agent loop keeps going and the model can decide what to do with "the search failed." Re-run in a minute if this happens repeatedly.

RAG answers seem to ignore the PDF entirely

Almost always means rag_ingest.py was never run, or was run against a different PDF than you're asking about. rag_query.py reads whatever is currently in chroma_db/ — re-run python3 rag_ingest.py against the PDF you actually want answers from before querying again.

Provider errors — AuthenticationError, Connection refused, model not found

Same causes and fixes as Module 1's Common Pitfalls — a missing or unsourced .env, or Ollama not running. See that module's Common Pitfalls section for the exact fix for each.

Teardown​

deactivate

There's nothing else required — no containers, no cloud resources. If you ran the bonus RAG lab, chroma_db/ is a local folder you can delete any time with rm -rf chroma_db — it's regenerated in full the next time you run rag_ingest.py. Leave Ollama running if you're continuing to later modules; nothing here needs any other cleanup.
