Deep Dive — Evals, Monitoring, and Honest Cost Accounting

The lab proved the endpoint answers. Part 2 proves something the lab didn't: that it answers correctly enough, on a batch of houses it never trained on, every single time you check — not just once, by hand, with two curl calls you eyeballed. Then it walks through the three signals a real team actually watches once a model like this is live, and closes with a worked example of the other thing that quietly breaks at scale — the bill.

Where this picks up

This page reuses labs/m7/.venv and api.py exactly as the lab left them. If you're arriving fresh:

cd labs/m7
python3 -m venv .venv && source .venv/bin/activate && pip install -r requirements.txt

Safe to re-run even if you already did this in the lab. Nothing here needs the server running — eval_harness.py calls the FastAPI app directly, in-process, so there's no uvicorn to start and no port to worry about.

1 — A real evaluation harness, not a manual spot-check​

The lab's Step 4 had you send two curl requests and eyeball whether the second price looked lower than the first. That's a sanity check, not an evaluation. It doesn't run again on its own, it doesn't tell you how wrong an answer was, and it can't tell a small, expected wobble apart from a real regression — a change that quietly breaks the model.

eval_harness.py runs the API against 50 real houses from the held-out test set — the exact same split api.py already made with random_state=42, so this batch never changes — and checks that the average error across all 50 stays under a tolerance:

python3 eval_harness.py

Expected output

Running eval harness against 50 held-out houses (regression mode: OFF)

  case 0   predicted $      71,912   actual $      47,700   error $      24,212
  case 1   predicted $     176,402   actual $      45,800   error $     130,602
  case 2   predicted $     270,966   actual $     500,001   error $     229,035
  case 3   predicted $     283,893   actual $     218,600   error $      65,293
  case 4   predicted $     260,466   actual $     278,000   error $      17,534

  ... (45 more cases not shown)

Mean Absolute Error across 50 cases: $57,849
Tolerance: $100,000

EVAL PASSED — mean error is within tolerance.

Case 0 here is X_test.iloc[0] — the exact same row Module 3's own script sanity-checked — and it reproduces Module 3's exact numbers: $71,912 predicted against $47,700 actual. Same model, same split, same answer.

Read the shape, not just the final line: each case shows a predicted price next to the real price and the gap between them, then the script averages that gap across all 50 cases into one number — the Mean Absolute Error, the exact metric Module 3 introduced — and compares it against a tolerance. This is the same idea as predict_house_price.py's own scoring step, just run automatically, against a fixed batch, with a pass/fail verdict instead of a number you have to interpret yourself.

Now break something on purpose. Real APIs disagree on the order of coordinates — some send [latitude, longitude], others [longitude, latitude] — and nothing in a JSON body stops a client from sending them swapped. --simulate-regression does exactly that to every request in the batch before sending it:

python3 eval_harness.py --simulate-regression

Expected output

Running eval harness against 50 held-out houses (regression mode: ON — Latitude/Longitude swapped)

  case 0   predicted $    -143,877   actual $      47,700   error $     191,577
  case 1   predicted $     -38,733   actual $      45,800   error $      84,533
  case 2   predicted $      47,983   actual $     500,001   error $     452,018
  case 3   predicted $      70,984   actual $     218,600   error $     147,616
  case 4   predicted $      39,834   actual $     278,000   error $     238,166

  ... (45 more cases not shown)

Mean Absolute Error across 50 cases: $218,566
Tolerance: $100,000

EVAL FAILED — mean error exceeds tolerance. A regression like this would ship silently without a harness like this one in the loop.

The mean error jumps well past the tolerance, and the script exits non-zero. That's the whole point of an eval harness: a bug like a swapped field doesn't crash anything and doesn't throw an exception — every request still returns 200 OK with a number that looks exactly like a real prediction. Nothing about that failure is visible from the outside unless something is actually checking the quality of the answer, not just whether an answer came back.

Analogy: a unit test checks that a function returns the right type of thing and doesn't crash. An eval checks that it returns the right answer, or something close enough to it — a distinction that matters because a model can be perfectly "working," in the sense of never throwing an error, while being quietly, systematically wrong. A team running this in CI wires the non-zero exit code into the same gate a failing test suite already blocks a deploy on — a regression like the lat/lon swap above never reaches production, because the pipeline that would have shipped it stops on this exact exit code.

2 — The three signals worth watching once it's live​

An eval runs before a change ships. Monitoring is what watches the system continuously after it has shipped, because a model that passed every eval on release day can still degrade in production without anyone touching the code — the lesson's drift scenario, made operational.

Three signals cover most of what actually matters for a served model:

  • Latency — how long a /predict call takes, end to end. A model that answers in 50ms and one that answers in 5 seconds are the same model, mathematically, and a completely different experience for whoever is waiting on the response. A latency chart that creeps upward over weeks, with no code change behind it, usually means growing request volume is quietly outrunning the server's capacity.
  • Error rate — the share of requests that fail outright: a 500 from a bug, a 422 from a malformed request, a timeout. The lab's Common Pitfalls section walked through several of these one at a time; monitoring is what counts how often they're actually happening in aggregate, across every request, not just the one you're staring at while debugging.
  • Prediction drift — whether the distribution of outputs is shifting over time, even when nothing is failing. If this model's average predicted price started climbing every month with no matching change in the input data, that is the lesson's drift concept showing up as a real, chartable number, well before anyone thinks to ask whether the model still needs retraining.

None of these three replace the eval harness above — an eval catches a bug before release; monitoring catches a problem that only shows up after release, sometimes weeks later, from real traffic an eval batch never captured.

3 — Honest cost accounting for LLM-backed apps​

Everything above applies to this module's regression model, where a wrong or slow prediction is the whole cost story. An LLM-backed feature has a second cost axis this model doesn't: Module 2 taught you that every token is billed, and that bill scales with how many people use the feature and how much each one of them uses it — not with how well the code was written.

Work through a small, honest example. Say a support-answering feature handles 2,000 requests a day, each one sending roughly 800 tokens of prompt (the question, plus system instructions and a little retrieved context) and receiving roughly 300 tokens back, at a provider price of $0.50 per million input tokens and $1.50 per million output tokens — prices deliberately picked as round, illustrative numbers, since real provider pricing changes often enough that memorizing a specific figure isn't the useful part of this exercise:

Input:  2,000 requests × 800 tokens  = 1,600,000 tokens/day × $0.50 / 1,000,000 = $0.80/day
Output: 2,000 requests × 300 tokens  =   600,000 tokens/day × $1.50 / 1,000,000 = $0.90/day
                                                                Daily total ≈ $1.70/day
                                                              Monthly total ≈ $51/month

Fifty-one dollars a month looks trivial, which is exactly why cost explosions catch teams off guard — the math above assumed the request count and the token counts both stay fixed. Module 5's reasoning-mode tradeoff breaks the second assumption directly: switch on a "thinking" mode for a task that doesn't need it, and the output-token count (the more expensive side of this bill) can multiply several times over for the same 2,000 requests, with no change in traffic at all. Feature success breaks the first assumption just as easily — the same feature going from 2,000 requests a day to 200,000, because it worked and people started using it, turns this exact $51 line item into roughly $5,100 a month, proportionally, with nothing in the code any different. The estimate above isn't precise enough to budget against on its own — real prompts vary in length, real usage isn't flat across every day — but the shape of it is the thing worth carrying forward: multiply requests by tokens by price, watch which of those three numbers is actually moving, and recompute before a feature ships to real volume, not after the first surprising invoice.

Where you will use this
  • A passing eval only proves a fixed batch stayed within tolerance — it says nothing about a bug an unattended change slipped in. Use it when: you're reviewing a pull request that touches a model, a prompt, or a feature's input schema — ask whether an eval like eval_harness.py ran against it, not just whether it compiled and the demo worked.
  • A model can return 200 OK on every request while being quietly, systematically wrong — errors and correctness are two different failure modes. Use it when: you're deciding what to monitor for a served model — error rate alone won't catch the lat/lon-swap class of bug; you need something checking answer quality too.
  • Latency, error rate, and prediction drift are the three signals that explain almost every "it used to work" incident. Use it when: an on-call report says a model "got worse" with no deploy behind it — check whether traffic grew (latency), something started failing (error rate), or the input data quietly shifted (drift), in that order.
  • Cost scales with requests × tokens × price, and any one of those three can move independently of the code. Use it when: you're asked to estimate what an LLM-backed feature will cost at real volume before it ships — do the multiplication explicitly, the way this section did, instead of extrapolating from a lab bill that only ever saw a handful of test calls.

Teardown​

Nothing new was seeded on this page beyond eval_harness.py's two runs — no files created, no background processes, no server left running. If you're moving on to Module 8, leave labs/m7/.venv as it is; nothing here needs any other cleanup.
