AI in Production — What Actually Breaks

Why doesn't "it works in my notebook" mean it's done?​

In Module 3 you trained a model, checked its error, and it looked good. That felt like the finish line. It's actually the starting line for a different problem: keeping that model correct, affordable, and actually working for people who aren't you.

A notebook run is a demo you gave once, to yourself, on data whose shape you already knew. Production is that same demo repeated thousands of times a day, for people you'll never meet, on input you never previewed — and it's someone's job to notice within minutes when it stops working. Everything in this module is about that gap: what breaks between "it ran once, correctly, for me" and "it keeps running, correctly, for everyone else."

By the end of this lesson, you can name the notebook-to-production gap, explain drift, degradation, hallucination at scale, and cost explosions as four separate ways a working system stops working, describe what an eval and a monitoring dashboard each actually watch for, and serve a real model behind an API the way today's lab has you do.

The notebook-to-production gap​

Analogy: think about cooking a dish once, for yourself, in your own kitchen. You already know the ingredients. You taste as you go. If something's a little off, you're the only one who notices, and you fix it before it matters. Now put that same recipe on a restaurant menu. It has to come out the same way for a stranger, every night, cooked by whoever's on shift, using ingredients that vary a little week to week — and if it goes wrong, the customer finds out before you do.

A trained model is the recipe. A notebook run is cooking it once for yourself. Serving it means someone else's environment runs your code, input arrives that you never previewed, failures need to be caught and logged instead of just appearing in a cell's output, and every request has to be handled — not just the ones that happen to look like your test data. Today's lab makes the "someone else's environment" part concrete: you take Module 3's exact housing-price model, the one you already trained and trusted, and wrap it in an API so a real client can ask it for a prediction instead of you running a script.

That loop on the right — watch, detect, respond — is the part a notebook never needed and production can't run without. The rest of this lesson walks through what it's actually watching for.

Drift and degradation: the ground moves under a working model​

Analogy: picture the housing-price model from Module 3, deployed and left alone for two years. Interest rates moved. A new transit line changed which neighborhoods people want to live in. The market it was trained on simply isn't the market anymore. Nobody touched the code. The world underneath the model moved, and the model didn't.

That's drift: the real-world relationship between the inputs and the right answer changes after you deployed, so a model that was accurate on launch day gets steadily less accurate without a single line of it changing. A close cousin is data drift — the inputs themselves start looking different from what the model trained on, like a service that starts getting requests from a country its training data barely covered. Degradation is what you actually observe: real-world accuracy sliding down over time, even though the model itself is byte-for-byte the one you shipped. Module 3's train/test split only ever proves a model was accurate on data collected at one point in time. Production keeps collecting new data every single day after that, and nothing guarantees the old pattern still holds.

Hallucination and cost, at scale​

Module 5 showed you why an LLM sometimes states something false with total confidence: at every token, it has to output something, whether or not it genuinely knows the answer. One wrong-but-confident sentence, caught by you while reading a single reply, is a minor annoyance. The same mechanism, running unattended inside a product that answers ten thousand customer questions a day, is a different problem entirely — a wrong sentence about a return policy, a price, or a safety instruction can reach a customer before anyone reviews it, and it will keep happening at whatever rate the underlying error rate implies, all day, every day.

Cost scales the same way, for a different reason. Module 2 taught you that every token is billed, and Module 5 showed you that a reasoning model spends extra tokens thinking before it answers. In a lab, that's a fraction of a cent per call. In a shipped feature — used by real people, at real volume — the identical per-token price turns into a bill your team has to justify, and a feature that got popular can be the exact reason a bill triples in a month. Nothing broke. It worked, and working at scale is its own kind of expensive.

The pattern underneath both

Hallucination and cost explosions look like different problems, but they share one cause: something that was rare or cheap enough to ignore in a single test run stops being ignorable once you multiply it by real traffic. That's the question worth asking about any AI feature before it ships: not "does this work," but "what does this cost, or how often does this go wrong, at the volume we actually expect?"

Evaluation and monitoring: how you know it's actually working​

Analogy: a pilot doesn't trust a plane will fly correctly just because it flew correctly during testing. There's a checklist run before every single flight, and a dashboard the whole time you're in the air — speed, altitude, fuel — so a problem gets caught while it's still small, not after it's the only thing anyone notices.

An eval — Module 2's term — is that pre-flight checklist: a fixed set of test cases with known-good answers, run against a change before it ships, so you find out it broke something before a customer does. Monitoring is the in-flight dashboard: continuous signals watched while the system serves real traffic, not just before a release. For a model in production, the signals worth watching are latency (how long a prediction takes), error rate (how often a request fails outright), and prediction drift (whether outputs are trending away from what your evals expect, the early warning sign for the degradation described above). The Deep Dive builds a small, runnable eval harness and walks through each monitoring signal in more depth.
