Frontier — The Agent Ecosystem: MCP, Tools & Agentic IDEs

The problem with hand-wiring every tool​

In Module 6 you built a real agent by hand: two tools, web_search and calculator, each with its own schema in tools.py, and a loop in agent.py that decided when to call them and when to stop. That's exactly how a first agent should be built — small, visible, every piece written by you.

Now scale that up to something closer to your actual job. You want an agent that reads issues from your team's GitHub repo, queries a production database, and posts a summary to Slack. Following Module 6's pattern, you'd write a schema and a wrapper function for the GitHub API, another for the database driver, another for Slack's API — and if a teammate built an agent last month that already talks to the same GitHub repo, none of that code is reusable. It was wired straight into their script, the same way web_search was wired straight into yours.

That's the gap this module fills: how the industry standardized the connection between an agent and the tools it uses, what the resulting tooling landscape looks like, and how multiple agents get combined once one agent isn't enough.

MCP: a standard, not a specific tool​

Analogy: before REST and OpenAPI became a shared contract, every web API had its own shape — its own auth scheme, its own error format, its own way of describing what endpoints existed. Every client that wanted to talk to a new API had to read its specific docs and write bespoke glue code, once per API, per client. REST plus an OpenAPI spec changed that: any client that understands the shared contract can talk to any API that publishes one, without custom code per pairing.

MCP (Model Context Protocol) does the same job for the connection between an agent and the tools or data it reaches out to. Instead of every agent framework inventing its own way to describe "here's a tool, here's its arguments, here's how to call it," MCP defines one shared shape. A tool, a data source, or a prompt template that speaks MCP can be plugged into any MCP-aware agent host — Claude Code, Claude Desktop, or any other client that implements the protocol — without writing integration code specific to that host.

MCP defines three roles:

  • Host — the application the model runs inside (Claude Code, Claude Desktop, an agentic IDE). This is where the agent loop from Module 6 actually lives.
  • Client — the part of the host that speaks MCP, built in once by whoever wrote the host.
  • Server — a small standalone program that wraps one tool or data source (GitHub, a filesystem, a database, Slack) and exposes it in MCP's standard shape.

Put plainly: Module 6's tools.py was two Python functions wired directly into one script. An MCP server does the same conceptual job — name, description, argument schema, a way to actually run the thing — but as a small standalone service that any MCP-speaking host can discover and call, instead of code glued into a single agent. Write the GitHub MCP server once; every agent on your team that speaks MCP can use it, the same way any REST client can call any documented API.

The agent stack, layer by layer​

Zoom out from one tool call to the whole system, and every agent — including your Module 6 agent — is built from four layers stacked on top of each other.

Map Module 6 onto this directly. The model was whatever provider you configured in .env — Gemini, or a local Ollama model. The tools & MCP layer was tools.py, hand-written instead of MCP-standardized, but doing the identical job: expose a callable thing with a schema. Memory was the running conversation inside that one script's context window — short-term only, in the base lab; Lab 5's optional RAG pipeline added a Chroma vector store, which is exactly the long-term half of this same layer. Orchestration was the loop in agent.py, deciding "call another tool" or "give a final answer," capped by MAX_ITERATIONS.

Nothing about this shape changes as systems get bigger. What changes is that the tools layer stops being one script's private code and becomes standardized, shared infrastructure — and orchestration can grow from one loop into several agents coordinating.

The agent tooling landscape​

Analogy: think about how a team picks up a new programming language. Some people write everything from a bare text editor and the compiler. Most people reach for an IDE that already knows how to run tests, format code, and manage dependencies — the same underlying work, with the repetitive parts built in. The agent tooling landscape has the same split.

A few categories are worth knowing by name, because you'll meet all of them on the job:

  • Agent frameworks package the loop you hand-wrote in agent.py — LangChain, LlamaIndex, CrewAI, OpenAI's Agents SDK, Anthropic's Claude Agent SDK. They give you the reason-act-observe loop, memory handling, and MCP support out of the box, so you configure a loop instead of writing one from scratch each time.
  • MCP servers and registries are prebuilt connectors — a GitHub server, a filesystem server, a Slack server, a database server — published once and reused across any host that speaks MCP, instead of a tools.py per project.
  • Agentic IDEs — Claude Code, Cursor, Windsurf, GitHub Copilot's agent mode — are MCP hosts purpose-built for software work. What makes one of these "agentic," rather than plain autocomplete, is the exact loop from Module 6: it can run a command, read the output, edit a file, run the tests, and decide on its own whether to keep going or stop — scoped to your codebase and your terminal instead of a search engine and a calculator.

Every one of these tools is doing the same reason-act-observe loop underneath. What differs is how much of the plumbing they build for you versus how much you write yourself, the way Module 6 did.

Multi-agent patterns, at a foundational level​

Module 6 already introduced the core idea: most of what you build is a single agent — one model, one toolset, one loop, start to finish. As a task grows past what one agent should reasonably own, some systems split the work across a multi-agent setup instead. Three patterns cover most of what you'll encounter:

  • Orchestrator + specialists — Module 6's triage-desk analogy: a router agent reads the incoming request and hands it to whichever narrower agent actually owns that kind of problem (a "billing" agent, a "technical support" agent), each with its own smaller toolset.
  • Sequential pipeline — one agent's output becomes the next agent's input, in a fixed order: a research agent gathers material, then a separate writing agent drafts from what it found.
  • Parallel fan-out / fan-in — several agents work the same task from different angles at the same time, and a final step combines their results — several reviewers checking the same document for different kinds of issues, then one summary of all the feedback.

All three are still built from the same single loop you already built in Module 6 — just more than one instance of it, coordinating through an orchestration layer instead of a human deciding by hand who does what next.

Where this leaves you​

You now have names for what you built by hand in Module 6, and for what changes as it scales: MCP standardizes the tools layer instead of leaving it as one script's private code, agent frameworks and agentic IDEs package the loop instead of leaving you to write it each time, and multi-agent patterns extend orchestration once one loop isn't enough. The lab has you place a set of real tools and products into the four-layer stack above — and because some of them deliberately span more than one layer, it's a genuine test of whether you can see the layers underneath the product name, not just repeat the pattern.
