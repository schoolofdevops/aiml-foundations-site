Deep Dive — LLMOps Pipelines and Tracing the Agent Loop

The lab added three things a real operator would ask for on a served model: a health check that actually checks something, a version endpoint, and one log line per request. That's the request/response layer — enough for the classic MLOps world the lesson mapped Module 3 and Module 4 into. Part 2 goes two layers past that: a stage-by-stage comparison of what an LLMOps pipeline actually replaces from a classic MLOps pipeline, not just what it adds, and what observability looks like once a single task fans out into several model and tool calls instead of one request and one response — the AgenticAIOps world Module 6's lab lives in.

Where this picks up

This page reuses labs/m8/.venv exactly as the lab left it. If you're arriving fresh:

cd labs/m8
python3 -m venv .venv && source .venv/bin/activate && pip install -r requirements.txt

Safe to re-run even if you already did this in the lab. Nothing here needs the API server running — both scripts below are plain Python, no uvicorn, no port, no API key.

1 — MLOps vs. LLMOps: the same discipline, a different artifact​

The lesson's table named what changes at a glance — data and weights versus prompt and context. This section walks the actual pipeline stages side by side, because "different artifact" undersells how much of the mechanics changes underneath.

python3 pipeline_stages.py

Expected output

Stage               MLOps                                 LLMOps
----------------------------------------------------------------
Source artifact     Training data + code                  Base model + prompt + retrieved context
Versioning unit     Dataset version + model weights       Prompt version + context/config version
Build step          Train / fit the model                 Assemble the prompt (system, few-shot, RAG)
Correctness check   Test suite (pass/fail assertions)     Eval suite (graded, threshold-based)
Registry            Model registry (weights + metadata)   Prompt/config registry (versioned templates)
Deployment unit     Serialized model file                 Prompt template + model/provider config
Retrain trigger     Scheduled retrain or drift alert      Prompt/context update or provider model swap

Read the Correctness check row first — it's the one that trips people up. A test suite checks that a function returns the type of thing you told it to and doesn't crash: a fixed input, one fixed expected output, pass or fail. An eval suite checks that an answer is good enough, graded against a rubric or a scored comparison, because two valid answers to the same prompt can be worded completely differently and both be correct. Module 7's eval_harness.py already did exactly this for a regression model — scoring Mean Absolute Error against a tolerance instead of checking one exact number. An LLMOps eval suite is the same idea, aimed at text: does this prompt version's output still pass a rubric, across a batch of real cases, after someone edited the system prompt.

Analogy: grading a multiple-choice exam is a test suite — one correct bubble, checked by a machine, no judgment involved. Grading an essay is an eval suite — there's a rubric, there's a range of acceptable answers, and "correct" is a graded quality, not a single matching string. The support-chatbot case study from the lesson broke a dozen question types with one prompt edit because it only had the multiple-choice check, never the essay grader.

The Registry row matters just as much in practice. An MLOps model registry tracks weights and training metadata — which dataset, which run, which metric. An LLMOps prompt registry tracks prompt templates and their configs the same way, versioned, so "what prompt is actually live" has as definite an answer as "what model weights are actually live" — the same question /version answers for a trained model, aimed at a prompt instead.

Same four stages, same order, different unit moving through each one. That's the "different artifact, same discipline" idea from the lesson, made concrete enough to build a pipeline from.

2 — Observability for agentic systems: tracing the loop, not just the request​

You already run this discipline for a chain of microservice calls: one user request fans out into several downstream calls, and request/response logging on the outermost call alone can't tell you which of those downstream calls was slow, or wrong, or the one that actually failed. Distributed tracing exists because "the request took 3 seconds" isn't useful — "step 3, the payments call, took 2.8 of those 3 seconds" is.

Module 6's agent loop has the identical shape. One task now means several model calls and tool calls chained together, and the lab's own logging only ever showed you the tool calls as they happened, printed once, for a single run you were watching live. Run it a thousand times a day, unattended, and "the agent got it wrong" tells you nothing about which of the five steps inside that one task actually caused it.

python3 agent_trace.py

Expected output

{"trace_id": "bed19974-b01f-4496-b777-59d44f91bb9a", "step": 1, "action": "reason", "detail": "need today's headline count", "duration_ms": 15.0}
{"trace_id": "bed19974-b01f-4496-b777-59d44f91bb9a", "step": 2, "action": "act", "tool": "web_search", "args": {"query": "top AI news today"}, "duration_ms": 12.9}
{"trace_id": "bed19974-b01f-4496-b777-59d44f91bb9a", "step": 3, "action": "observe", "detail": "3 results returned", "duration_ms": 15.0}
{"trace_id": "bed19974-b01f-4496-b777-59d44f91bb9a", "step": 4, "action": "reason", "detail": "have enough to answer", "duration_ms": 15.0}
{"trace_id": "bed19974-b01f-4496-b777-59d44f91bb9a", "step": 5, "action": "respond", "detail": "final summary returned", "duration_ms": 11.9}
trace_id=bed19974-b01f-4496-b777-59d44f91bb9a steps=5

(trace_id and the per-span duration_ms values are generated fresh on every run — the shape of the output, not these exact values, is what to expect.)

Every line is one span — a name a tracing backend uses for one step's record: a trace_id shared by every span in the same task (so they can be grouped back together after the fact, the same way a distributed trace groups calls across services), the step number, the action taken, and how long it took. The scripted loop here always takes the same five steps — reason, act, observe, reason, respond — deterministically, so the trace is reproducible without a real model call or an API key. A real agent's trace has the same shape, with a variable number of steps depending on what the task actually needed.

With every step traced this way, four signals become answerable that a single request/response log never could:

  • Steps per task — the lesson's runaway-agent case study, made visible. A task that normally takes three spans and starts regularly taking nine is a loop doing more work than it should, long before it shows up as a cost or latency complaint.
  • Tool-call error rate, per tool — not "the agent failed," but "the web_search tool specifically is failing on 12% of calls," which tells you exactly where to look.
  • Cost per completed task, not per request — a task with five model calls inside it costs five times what the outermost request/response log would suggest if you only billed the final reply.
  • Whether the loop actually stopped where you expect — Module 6's MAX_ITERATIONS cap is a safety net for a loop that won't stop on its own. Tracing is what tells you that cap is actually being hit in production, and how often — a safety net nobody is watching is just an assumption.
Where you will use this
  • An eval suite grades whether an answer is good enough; a test suite only checks it didn't crash. Use it when: you're reviewing a pull request that edits a prompt or a system message — ask whether it ran against an eval suite covering more than the one complaint that triggered the edit, the way the lesson's chatbot case study didn't.
  • A prompt registry answers "what's actually live" for a prompt the same way a model registry answers it for weights. Use it when: you're debugging a "it worked yesterday" report on an LLM-backed feature — check which prompt version is actually deployed before assuming the model provider changed something.
  • Request/response logging on the outer call can't tell you which inner step of an agent loop caused a bad or slow answer — you need a span per step, tied together by one trace_id. Use it when: you're setting up observability for anything that calls an LLM more than once per task — a multi-step agent, a retrieval-then-generate pipeline, any loop with more than one hop.
  • Steps-per-task and tool error rate are the two signals that catch a runaway or misbehaving agent loop before cost or latency does. Use it when: an agent-based feature's bill or response time climbs with no traffic increase — check the trace data for step count and per-tool error rate before assuming it's a model or a provider issue.
