MLOps, LLMOps & AgenticOps — The Deep Dive

Who actually runs this, once it's real?​

Count what you've built so far. Module 3 trained a model that predicts a price. Module 4 trained one that reads a handwritten digit. Module 5 called an LLM. Module 6 built an agent that decides its own next step. Module 7 put one of those models behind an API. Six real things, each working on your laptop. None of them answer the next question on their own: who keeps this running once it's serving real people, and what do the people who do that job actually call it?

That's what this module answers. Not a new skill to build — a map of the discipline that keeps everything you've already built alive, plus a clear line to the next course this one was built to lead into.

By the end of this lesson, you can define MLOps and trace how it grew into LLMOps and AgenticAIOps, explain where each one fits and how MLOps differs from the DevOps you already know, describe what an MLOps engineer actually does all day, and place every lab you've run so far on the right side of that map.

What is MLOps, and how did it become LLMOps and AgenticAIOps?​

Analogy: you already know DevOps — build the code, test it, ship it, watch it, fix what breaks. Now picture the same discipline, except the thing you're shipping isn't only code. It's code plus a slab of training data plus a model file that came out of that data — and that model file can quietly get worse over time even when nobody touches a single line of code, because the real world it's predicting against keeps moving. That extra, moving part is the whole reason MLOps exists as its own discipline instead of just being DevOps with a different file extension.

MLOps is DevOps practice applied to a system whose main artifact is a trained model, not just code: version the data and the model alongside the code, automate training the way you'd automate a build, test with evals that grade an answer instead of a pass/fail assertion, and monitor for the model getting quietly worse — drift, from Module 7 — not only for the server going down. Everything in Module 3 and Module 4's labs is this world: a model you trained yourself, from data you controlled.

Then Module 5 changed what "the model" even means. You stopped training anything. You called a model someone else already trained, and the thing you actually controlled was the prompt and the context around it. Operating that world is LLMOps — the same discipline, aimed at a different artifact: prompt versions instead of model weights, eval suites that grade an answer's quality instead of a fixed test set, and retrieval pipelines (RAG, from Module 5) that need their own freshness checks.

Module 6 added one more layer on top: an agent that decides its own next step, calling tools across several turns instead of answering once. Operating that is AgenticAIOps (also called AgenticOps) — everything LLMOps already covers, plus watching the loop itself: how many steps a task takes, which tool calls fail, and whether the agent is doing something it shouldn't, not just whether one reply was accurate.

Each stage doesn't replace the one before it — it adds a layer on top. An LLMOps team still cares about everything an MLOps team cares about for any model it trains or fine-tunes; an AgenticAIOps team still cares about everything LLMOps covers for every model call inside the loop. Read the diagram left to right as "what you're now responsible for," not as one discipline retiring the last one.

MLOps vs. LLMOps vs. AgenticAIOps — and where DevOps fits​

The three disciplines from the last section aren't picking between options — they're answering "what am I actually operating?" for a given system. Put side by side, what changes at each layer is what gets versioned, what gets tested, and what gets watched once it's live:

MLOpsLLMOpsAgenticAIOps
What you versiondata + model weightsprompt + context/configall of LLMOps + the tool/loop config
What you testa fixed test set, pass/failan eval suite, gradedeval suite + loop-level checks (step count, tool errors)
What you watch liveaccuracy, driftanswer quality, cost per callall of LLMOps + steps per task, runaway loops
This course's labsModule 3, Module 4Module 5Module 6

A system rarely stays in exactly one row. Module 9's capstone calls an LLM, runs an agent loop, and retrieves from a PDF — whoever operates it in production needs all three disciplines at once, layered the way the diagram above showed.

Now the DevOps-vs-MLOps question directly. What's the same is most of what you already do — build, test, deploy, automate, version control, monitor. MLOps doesn't throw any of that out. What's different is the artifact and what "broken" means for it. A code deploy is deterministic — the same commit produces the same binary every time, and a test suite is a fixed pass/fail check against it. A model's "build" step is training, which isn't fully deterministic and can take hours instead of seconds; its "test suite" is an eval that grades an answer's quality instead of checking it against one exact expected output; and, the part that catches teams off guard, it can go from working to wrong with zero code change, because the real world the model predicts against moved (Module 7's drift). A deploy pipeline that only watches "did the process crash" misses that completely.

That gap is exactly the job an MLOps engineer does. They sit between the person who trained the model and the team running production — building the pipeline that takes a model out of someone's notebook and makes it repeatable: automated retraining, a model registry that tracks which version is actually live, deployment automation, and the monitoring and retraining triggers that catch drift before a customer does. It's a platform-engineering job aimed at models instead of application code, and the muscle you're using is the same DevOps muscle you already have, redirected at a different kind of artifact.

Real MLOps case studies, briefly​

These are illustrative, not deep case studies — the shape of a real incident in each discipline, in a couple of sentences.

A retail recommendation team shipped a model that scored well in testing, then watched click-through quietly slide for two months before anyone noticed — nobody had wired up drift monitoring, so the first signal was a business metric, not an engineering one. The fix was automated retraining triggered by a drift threshold instead of a calendar, so it now happens before revenue moves, not after.

A support-chatbot team edited a system prompt to fix one customer complaint, shipped it straight to production, and broke a dozen other question types that prompt was quietly relying on — there was no eval suite to catch the regression, only customers finding it. They added a small eval suite that runs before every prompt change, the LLMOps equivalent of a test suite gating a code deploy.

An ops-automation team built an agent to file tickets automatically, and it once took nine tool calls to do what should have taken two, silently burning cost on a loop that never should have run that long. Nobody could see it happening, because they were only logging the final answer, not each step. Step-level tracing — the exact idea the Deep Dive builds out in full — is what let them see it and add a cap.

Where the MLOps Bootcamp picks up​

This module gave you the map and the vocabulary — MLOps, LLMOps, AgenticAIOps, drift, eval suites, the MLOps engineer's job. It didn't have you build a training pipeline, a model registry, or an automated retraining trigger by hand — that's real, multi-week engineering work, not a module-length lab. That's exactly where the School of DevOps & AI MLOps Bootcamp picks up: the same three case studies above, but you build the actual pipeline that would have caught each one, end to end, on a system that keeps running instead of one you tear down after an hour.

What carries forward

The three case studies above map directly onto what the Bootcamp builds: automated retraining for the drift case, an eval-gated deploy pipeline for the prompt-regression case, and step-level tracing for the runaway-agent case. If any of those sounded like a problem you'd rather solve with your hands than just read about, that's your signal to look at it next.
