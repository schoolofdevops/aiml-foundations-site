Lab — Instrument Your API for Operations

Goal: Take Module 7's exact FastAPI app — the one that already serves real predictions over HTTP — and add what an MLOps engineer would ask for before trusting it in production: a /health endpoint that actually checks something, a /version endpoint, and a request-logging hook. Then sketch the CI + retraining loop this API would sit inside for real.

Time: ~20 minutes Prerequisites: Module 7's lab, so you recognize the parts of api.py that don't change. This module needs its own environment — you are not reusing Module 7's venv.

Step 1 — Create this module's own venv​

Every module's lab lives in its own folder with its own dependencies. From the root of the course repo (where you cloned aiml-foundations-labs):

cd labs/m8
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

Step 2 — Read what's unchanged, then what's new​

Open the file:

cat api.py

The training block and the /predict endpoint are Module 7's api.py, untouched — same dataset, same LinearRegression, same request and response shape. If you compare this file against Module 7's, that part doesn't move.

What's new sits above and around it. First, logging setup, near the top of the file:

file: labs/m8/api.py

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)s %(message)s",
)
logger = logging.getLogger("house_price_api")

basicConfig's default handler writes to stderr — the same place uvicorn's own INFO: lines already go, so you don't need a second terminal or a log file to see it. Every /predict request logs one line through this logger, added at the end of the existing predict() function:

file: labs/m8/api.py

logger.info("predict request shape=%s prediction=%s", row.shape, result)

Next, the two new endpoints:

file: labs/m8/api.py

@app.get("/health")
def health():
    is_fitted = hasattr(model, "coef_") and model.coef_ is not None
    return {"status": "ok" if is_fitted else "unavailable", "model_fitted": is_fitted}


@app.get("/version")
def version():
    return {
        "api_version": API_VERSION,
        "model_type": type(model).__name__,
        "features": list(X.columns),
    }

/health doesn't just return {"status": "ok"} unconditionally — a fitted LinearRegression exposes a coef_ array; one that never finished training doesn't. This is what tells /health apart from a check that always passes even if training silently failed. /version answers the question an incident channel asks first — "what's actually deployed right now?" — with a real answer: the API version string (API_VERSION, a constant near the top of the file), the model class, and the feature names it expects.

Step 4 — Check /health and /version​

In your second terminal, from labs/m8:

curl http://127.0.0.1:8000/health

Expected output

{"status":"ok","model_fitted":true}

model_fitted should read true — the model trained successfully at startup. Now check what's actually deployed:

curl http://127.0.0.1:8000/version

Expected output

{"api_version":"1.1.0","model_type":"LinearRegression","features":["MedInc","HouseAge","AveRooms","AveBedrms","Population","AveOccup","Latitude","Longitude"]}

Both responses come back with no request body and no query parameters — that's deliberate. A liveness check and a version check are things a load balancer or an incident channel calls constantly, without knowing anything about this particular API's business logic.

Step 5 — Call /predict and watch the log line appear​

curl -X POST http://127.0.0.1:8000/predict \
  -H "Content-Type: application/json" \
  -d '{"MedInc": 8.3252, "HouseAge": 41.0, "AveRooms": 6.984127, "AveBedrms": 1.02381, "Population": 322.0, "AveOccup": 2.555556, "Latitude": 37.88, "Longitude": -122.23}'

Expected output (the JSON reply in this terminal; a matching log line lands in your first terminal, the one running uvicorn, at the same moment — check there next)

{"predicted_price":415194.31}

And in the first terminal, alongside the usual uvicorn access-log line:

2026-08-15 04:46:47,872 INFO predict request shape=(1, 8) prediction=415194.31
INFO:     127.0.0.1:63206 - "POST /predict HTTP/1.1" 200 OK

Switch to that first terminal. Alongside uvicorn's usual INFO: 127.0.0.1 ... "POST /predict HTTP/1.1" 200 OK line, you should now see a second line stamped house_price_api, built from the logger.info(...) call in Step 2: a timestamp, the shape of the request — (1, 8), one row of eight features — and the prediction it returned. Send two or three more requests with different numbers and watch a new line land for each one. This is the smallest version of what a real request-logging pipeline does: one structured record per call, in a form something downstream (a log aggregator, an alert rule, an on-call dashboard) can actually parse.

The CI + retraining loop this API would sit inside​

Everything above runs on your laptop, by hand. A real deployment of this same API sits inside a loop that runs on its own:

Trace it against what you just built. /health is what DEPLOY checks before routing any real traffic to the new instance — a deploy that skips this step can send requests to a copy of the API that never finished training. /version is what MONITOR reports back during an incident, so whoever's on call knows exactly what's live without guessing. The request-logging line from Step 5 is the raw material MONITOR actually watches — without it, drift and error-rate alerts have nothing to compute from. RETRAIN isn't code you wrote today; it's the automated retraining an MLOps engineer wires up once monitoring proves a model needs it, closing the loop back into CI so the retrained model gets tested again before it deploys, not after.

Common Pitfalls​

Forgetting to bump API_VERSION on a real deploy

/version is only useful if the number actually changes when the code does. It's a plain string constant in api.py — nothing enforces that you update it. A real pipeline ties this to something automatic, like the git commit SHA or a CI build number, specifically so nobody has to remember to bump it by hand before every deploy.

Logging PII or other sensitive data by accident

The logging line in this lab logs a request's shape — (1, 8) — not the actual feature values, on purpose. It would have been just as easy to log features.model_dump() directly, and for this dataset that's harmless. For a real system handling names, emails, or account numbers, logging the full request body by default is a genuine incident: that data now sits in plain text in every log aggregator downstream, often retained far longer and read by far more people than the original request ever was. Log the shape, the prediction, and a request ID — not the payload — unless you have a specific, reviewed reason to log more.

A /health endpoint that doesn't actually check anything

The easiest way to write a health check is return {"status": "ok"} with no logic at all — and it will pass every single time, including the time training silently failed and /predict is about to return errors to every real caller. This lab's /health checks coef_ specifically so a broken deploy shows up as model_fitted: false instead of a green check a load balancer trusts right up until the first real request fails.

Teardown​

Stop the server with Ctrl+C in the terminal running uvicorn, then:

deactivate

Nothing else to clean up — the logging hook writes to stderr, not to a file, so there's no log file left behind. The cached dataset under ~/scikit_learn_data/ (from Module 3) is harmless to leave in place.
