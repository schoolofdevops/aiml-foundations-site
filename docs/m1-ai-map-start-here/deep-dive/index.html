Deep Dive — The Wire Under the AI Map

The lab proved you can get a real answer out of a model with three lines of Python. Part 2 goes underneath that print(...) statement to three things a working engineer actually needs once "make a model answer" stops being the interesting part of the job: the raw wire your SDK call rides on, the metering that decides what a call actually costs, and the exact JSON field that turns a single call into an agent loop. None of this changes what you already ran — it's the same script, read more closely.

Where this picks up

This page reuses the exact environment from the lab: labs/m1/.venv and whichever provider you configured in .env (or the Ollama defaults if you configured nothing). If you're arriving fresh:

cd labs/m1
python3 -m venv .venv && source .venv/bin/activate && pip install -r requirements.txt

Safe to re-run even if you already did this in the lab — venv and pip install are both idempotent.

1 — What chat.completions.create() actually sends​

Analogy: the SDK method call is a courier van pulling up to your door with a package. The wire — the raw HTTP request and JSON body underneath it — is the paved road every provider's van drives on. Ollama, Gemini, OpenAI, Grok, and Claude each run a completely different van company, but they all agreed to drive on the same road. That agreement is the only reason the same three lines of Python worked no matter which one you picked in the lab.

Call the endpoint directly, bypassing the SDK entirely, using whichever provider you configured (defaults shown are for local Ollama):

curl -s "${LLM_BASE_URL:-http://localhost:11434/v1}/chat/completions" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer ${LLM_API_KEY:-ollama}" \
  -d "{\"model\":\"${LLM_MODEL:-qwen2.5:1.5b}\",\"messages\":[{\"role\":\"user\",\"content\":\"Reply with the single word OK.\"}]}" \
  | python3 -m json.tool

Expected output (id, created, and system_fingerprint will differ on every call; the shape — choices, message.content, finish_reason, usage — is what to look for)

{
    "id": "chatcmpl-813",
    "object": "chat.completion",
    "created": 1785908061,
    "model": "qwen2.5:1.5b",
    "system_fingerprint": "fp_ollama",
    "choices": [
        {
            "index": 0,
            "message": {
                "role": "assistant",
                "content": "OK"
            },
            "finish_reason": "stop"
        }
    ],
    "usage": {
        "prompt_tokens": 36,
        "completion_tokens": 2,
        "total_tokens": 38
    }
}

response.choices[0].message.content — the one field first_call.py printed — is one small piece of a much larger object. Look for id (a per-call identifier your logs would key on), model (the exact model that actually served the request, useful when a provider silently routes you to a different variant), finish_reason (stop for a normal completion, length if the response got cut off, tool_calls if the model wants to call a tool instead of answering — more on that in section 3), and usage, which section 2 is about.

2 — The meter the ML region never needed​

Analogy: a classical ML model's predict() call is a vending machine — put in your features, get out one number, no meter running anywhere. An LLM call is a taxi: the meter runs for every word you send in and every word it sends back, and that meter reading is exactly what your bill is built from.

Print just the usage block from the same call:

cd labs/m1 && source .venv/bin/activate
python3 -c "
import os
from openai import OpenAI
client = OpenAI(base_url=os.environ.get('LLM_BASE_URL', 'http://localhost:11434/v1'), api_key=os.environ.get('LLM_API_KEY', 'ollama'))
r = client.chat.completions.create(model=os.environ.get('LLM_MODEL', 'qwen2.5:1.5b'), messages=[{'role': 'user', 'content': 'Reply with the single word OK.'}])
print(r.usage)
"

Expected output (token counts will vary slightly with prompt/response length, but the three fields are always present)

CompletionUsage(completion_tokens=2, prompt_tokens=36, total_tokens=38, completion_tokens_details=None, prompt_tokens_details=None)

prompt_tokens is what your input cost, completion_tokens is what the generated answer cost, and total_tokens is the sum a provider bills against. Module 5 covers how text turns into tokens in the first place; Module 7 covers what this meter looks like at production scale, when a single verbose system prompt repeated across a million calls turns into a real number on an invoice. The thing worth internalizing now is simpler: crossing from the ML region into the LLM region doesn't just get you a chattier model — it changes the resource model entirely, from "compute you already own" to "a cost that accrues per call."

3 — The hook the agent loop watches​

Analogy: picture a support rep at a desk. Most of the time they answer you directly — that's message.content. Sometimes, instead of answering, they write "check order #4471 in the system" on a slip of paper and hand it to whoever's listening for that slip — that's message.tool_calls. Nothing about the desk changes. It's the same rep, the same message object; only which field carries the payload changes, and that single field is the entire mechanical seam between "the model answered" and "the model wants to act."

You didn't pass a tools list in Steps 1–2, so tool_calls on your responses is empty or absent — there was nothing to call. The shape of a request that offers the model something to call looks like this (illustrative — you'll build the working version in Module 6):

{
  "model": "qwen2.5:1.5b",
  "messages": [{"role": "user", "content": "What's 47 * 12?"}],
  "tools": [{
    "type": "function",
    "function": {
      "name": "calculator",
      "description": "Evaluate a basic arithmetic expression",
      "parameters": {"type": "object", "properties": {"expression": {"type": "string"}}}
    }
  }]
}

When a model decides to use calculator instead of answering directly, message.tool_calls comes back populated with the function name and the arguments it wants to call it with — and your code, not the model, is responsible for actually running the function and feeding the result back in. That "wait for tool_calls, run it, feed the result back, ask again" loop is an agent. Everything else — memory, planning, multiple tools — is elaboration on that one loop.

Where you will use this
  • The raw wire is the same JSON contract regardless of the SDK you or a teammate chose. Use it when: you're debugging a library-level bug (a wrapper swallowing an error, a version mismatch) and need to rule the library out — curl the endpoint directly and compare.
  • The usage block is the only ground truth for what a call actually cost. Use it when: a production LLM feature's cost spikes and you need to know whether it's more calls, longer prompts, or longer completions before you can fix the right thing.
  • tool_calls is the literal field an agent loop polls, not a metaphor. Use it when: you're debugging an agent that "isn't calling my tool" — check whether tool_calls ever appears in the raw response before assuming your loop code is the bug.

Teardown​

Nothing new was seeded on this page beyond the two throwaway calls above — no files, no background processes. If you're moving on to Module 2, you can leave labs/m1/.venv and any running Ollama server as they are; nothing here needs cleanup beyond what the lab's own Teardown already covered.
