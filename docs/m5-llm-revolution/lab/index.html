Lab — Your First LLM API Call, as a Reusable Tool

Goal: Turn Module 1's fixed 3-line LLM call into a small command-line tool that answers any question you give it — the first reusable piece of the assistant you'll keep extending through the rest of this course.

Time: ~15 minutes Prerequisites: Module 1's lab, completed at least once — this lab reuses the exact provider you configured there. If you're in a brand-new terminal session, you'll re-source that configuration in Step 1.

Step 1 — Create this module's venv, and reuse Module 1's provider​

Every module's lab lives in its own folder with its own dependencies, so Module 5 gets its own venv, even though it needs the same one package Module 1 did. From the root of the course repo (where you cloned aiml-foundations-labs):

cd labs/m5
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

Step 2 — Ask it a real question from the command line​

This is the whole point of the module: the fixed sentence in Module 1's first_call.py is now whatever you type.

python3 qa_cli.py "What's the difference between a token and a parameter?"

Expected output (a real, generated answer — exact wording will differ every run; the small local model used by the $0 default won't always get the LLM-specific meaning right, as it didn't here)

A "token" and a "parameter" are terms often used in web development, but they have slightly different meanings:

1. **Token**:
   - A "token" is usually an input submitted to authorize access or perform some action on a webpage.
   - It is typically displayed on the webpage for users to select their choice from dropdown lists or radio buttons.
   ...

2. **Parameter**:
   - A "parameter" is a set of information that you send to the web application or service.
   - You don't usually see a parameter by itself; it's always sent on the request data.

In summary, in the context provided so far, the term "token" specifically refers to a field like `country`, which represents user selection. The parameters are the additional information that come along with this action (in our case, when we submit one item from a list of options).

Open the file and look at what changed since Module 1:

cat qa_cli.py
What's new vs. first_call.pyWhy
question = " ".join(sys.argv[1:])The question comes from what you typed on the command line, not a string baked into the file
def ask(question: str) -> str:The client-construct-call-return sequence is now a function you can call again for a different question, not a one-shot script

Everything else — constructing the OpenAI client, calling chat.completions.create, reading response.choices[0].message.content — is exactly Module 1's 3-line pattern, just wrapped in a function you can call with any question.

Step 3 — Ask it interactively​

Run the script with no arguments, and it prompts you instead of reading from sys.argv:

python3 qa_cli.py

Expected output (the prompt it waits on — type a question, press Enter, and the same kind of generated answer as Step 2 prints below it)

Ask a question: <type your question here, then press Enter>

To run this same interactive path as one copy-runnable command instead — piping a question in rather than typing it live, which is also how lab-validation exercises this step:

echo "What is retrieval-augmented generation?" | python3 qa_cli.py

Expected output (a real, generated answer — exact wording will differ every run)

Ask a question: Retrieval-Augmented Generation (RAG) is a type of machine learning task that typically involves combining the power of two models:
1. A generator model: This produces new, original pieces of content like text or images based on existing inputs.
2. A retriever model: This searches through a large repository for previously created material and selects it to best meet the task requirements.

The process works as follows:
- The user provides input data that is used to generate a response using the generator model.
- The generated answer is then compared to relevant content retrieved from a massive, pre-trained dataset stored in Hugging Face's Transformers library.
- If the generated item meets certain criteria (e.g., high quality or being consistent with known categories), it replaces the input for further processing; otherwise, the process starts again for more attempts until finding a satisfactory match.
...
RAG represents an exciting frontier in artificial intelligence where AI can learn to integrate existing knowledge with innovative generation, enhancing its ability to produce high-quality content with a much richer scope of application than traditional techniques alone.

Step 4 — Shape the answer with a system prompt​

Try it: add a system prompt

Open qa_cli.py and change the messages list inside ask() from:

messages=[{"role": "user", "content": question}],

to:

messages=[
    {"role": "system", "content": "Answer in one short sentence. No preamble."},
    {"role": "user", "content": question},
],

Re-run Step 2's command. Same question, a noticeably shorter answer — this is the lesson's system prompt concept, made real: one extra message that steers every answer, without touching the question itself. Put the original single-message list back before moving on.

Common Pitfalls​

ModuleNotFoundError: openai after a successful install

You likely activated a different venv than the one you installed into, or you're in a brand-new terminal where .venv was never activated this session. Run source .venv/bin/activate again from inside labs/m5 — you should see (.venv) in your prompt before running the script.

python3 qa_cli.py hangs with no output

You ran it with no arguments, which is Step 3's interactive mode — it's waiting on input() for you to type a question and press Enter. If you meant Step 2's argument form, Ctrl-C out and re-run with your question in quotes.

Not handling empty input

Press Enter at the Ask a question: prompt with nothing typed, or pipe in an empty string, and a naive version of this script would either send a blank question to the API (wasting a call for nothing useful) or crash outright — piping EOF straight into input() with no handling raises EOFError: EOF when reading a line. qa_cli.py guards against both: it treats a blank or missing answer the same way, with one message, instead of a stack trace. If you extend this tool and add your own input path, remember every new source of "the question" needs the same empty-input check.

Hardcoding a question instead of taking one as an argument

If you're extending this tool for your own use and find yourself editing a PROMPT = "..." line at the top of the file every time you want to ask something different, you've undone the point of this lab. Keep the question as a parameter — a CLI argument, a function argument, an input() prompt — never a hardcoded string inside the logic.

Printing the whole response object instead of the answer

response is a structured object with metadata — model name, token usage, a list of choices — not a string. print(response) prints a wall of that structure instead of the answer a person asked for. Always print response.choices[0].message.content (or, as ask() does here, return it and print the return value).

Provider errors — AuthenticationError, Connection refused, model not found

These are all Module 1 setup issues, not new to this lab — see Module 1's Common Pitfalls for the fix for each. The most common cause here specifically is a fresh terminal that never ran source .env or source ../m1/.env again.

Teardown​

deactivate

There's nothing else to tear down — no containers, no cloud resources. qa_cli.py is yours to keep and reuse outside this course; it's a genuinely small, working Q&A tool. If you added a system prompt in Step 4 and want to keep it, that's fine — nothing later in the course depends on this file being in its original state.
