Graduation & Your Three Paths — MLOps, LLMOps & Agentic DevOps

Nine modules ago, could you have answered this?​

Someone asks you, in a review or a vendor call: "is that machine learning, or a language model, or an agent?" Module 1 opened with that exact question, and you probably couldn't answer it without hedging. You can now. Along the way you trained a model that predicts a number, built a small neural network, called a real LLM from your own code, watched an agent reason across several steps and call tools on its own, and wired all of that into one assistant you served behind an API and tried, on purpose, to break.

That's not a study plan finished. It's five real things, built with your own hands, that correspond to five real jobs happening in production systems right now. This module does three things before you close the course: recaps what each of those five things actually is in a real AI system, gives you a final practice test to check what stuck, and lays out the three paths that each pick up a different piece of what you just built and take it further.

Five projects, one thread​

Each project you built lines up with a real category of work a production AI team owns. None of them are toy exercises that only existed for the lab — they're smaller, honest versions of what runs at scale.

  1. A predictor (Module 3) — a linear regression that forecasts a number, a house price, from historical data. In a real company, this is the shape of demand forecasting, churn scoring, or any system that turns a spreadsheet of past outcomes into a number for tomorrow.
  2. A digit classifier (Module 4) — a small neural network that reads a handwritten digit and names it. This is the shape of image recognition, fraud flagging on a transaction, or any system that has to learn its own features from messy, unstructured input instead of neat rows and columns.
  3. An LLM-powered tool (Modules 1 and 5) — your first real API call to a language model. This is the shape of every "AI copilot" feature bolted onto a product today: a single call in, a generated answer out.
  4. An autonomous agent with tools and retrieval (Module 6) — a system that reasons in steps, calls a calculator or a search tool on its own, and looks answers up in a document instead of guessing. This is the shape of agentic coding tools, research assistants, and ops automation that files a ticket without a human clicking through each step.
  5. A capstone assistant, served behind an API (Modules 7 through 9) — the LLM call, the agent loop, and retrieval, wired together and put behind the same kind of endpoint a real client would call. This is the shape of the actual product a team ships, not just the model behind it.

Two of these — the predictor and the classifier — stayed standalone; forcing a house-price model into a chat assistant would have been a fake connection, not a real one. The other three converged into one capstone on purpose, because that's an honest picture of where a lot of production AI work is heading: not a model in isolation, but a model wrapped in tools, memory, and a serving layer.

Check what stuck​

Before you look at what's next, spend the time to find out what actually stuck. Today's lab is a 30-question, exam-style AI Foundations Check — a final practice test covering every module from here back to Module 1, each question with an explained answer, not just a right/wrong mark. It also leaves you with a course reference card, a condensed cheat sheet of every module's key terms, worth keeping open the next time an AI product page or a vendor pitch uses one of them.

Same rotation, three specializations​

Analogy: picture an engineer who just finished a structured rotation through every part of a company's stack — a stint on data pipelines, a stint on backend services, a stint on the platform team, a stint on-call. That rotation didn't turn them into a specialist in any one of those areas. It gave them something more useful at this exact point: enough hands-on time in each to know which one they actually want to go deep on next, and enough shared vocabulary to work well with whoever they land next to.

That's what the last nine modules did. You didn't just read about MLOps, LLMOps, and what Module 8 called AgenticAIOps — you built one small, honest piece of each discipline's actual subject matter: a trained model, an LLM call, and an agent loop. The three paths below are where each of those pieces gets taken from "a lab you tore down after an hour" to "a system you run, monitor, and keep alive for real people." The course names for the three paths — MLOps, LLMOps, and Agentic DevOps — map directly onto the three operational disciplines Module 8 named as MLOps, LLMOps, and AgenticAIOps. Same subject, the second one is just how the follow-on courses are titled.

MLOps — keeping a trained model right after launch day​

Module 3's predictor and Module 4's classifier both proved themselves once, in a notebook, on data collected at one point in time. Module 7 named the real risk: the world underneath a deployed model keeps moving, and nothing guarantees the pattern it learned still holds a year later. Module 8's retail case study was exactly this — click-through quietly sliding for two months before anyone noticed, because nobody had wired up drift monitoring. The MLOps path picks up here: versioning data and model weights, automating retraining, and building the monitoring that catches degradation before a customer, or a business metric, does.

LLMOps — keeping a prompt-and-retrieval system honest​

Module 5's LLM call and its RAG pipeline don't have weights you trained — what you actually control is the prompt, the context, and what gets retrieved into it. Module 8's support-chatbot case study showed what happens without discipline around that: one system-prompt edit, shipped straight to production, quietly broke a dozen other question types nobody thought to re-check. The LLMOps path is the eval suite that would have caught that before it shipped, plus retrieval pipelines that get their own freshness checks instead of being assumed to work forever.

Agentic DevOps — keeping a multi-step loop bounded​

Module 6's agent decides its own next step, which is exactly what makes it powerful and exactly what makes it capable of going wrong quietly. Module 8's ops-automation case study is the pattern: an agent that should have taken two tool calls to file a ticket instead took nine, silently burning cost, and nobody could see it happening because only the final answer was being logged, not each step. The Agentic DevOps path is step-level tracing, loop caps, and the guardrails around prompt injection Module 6 first named — everything LLMOps already covers, plus watching the loop itself.

None of these replace the other two

A real system rarely lives in exactly one row. Your own capstone calls an LLM, runs an agent loop, and retrieves from a PDF — whoever runs it in production needs pieces of all three disciplines at once, the same way Module 8 said. Picking a path means picking where you go deep first, not picking the only thing you'll ever need to know.

Where to go from here​

If you want to go deeper on what's moving in the field right now — new engineering disciplines, the agent tooling ecosystem, agentic IDEs — before committing to one of the three paths, the Frontier track picks up next and ends in its own, more detailed path-selection lab that maps your goals to a specific next course. If you already know which of the three you want, each one is a standalone next course from the School of DevOps & AI, picking up exactly where its matching module left off: the MLOps Bootcamp from Module 3 and 4's foundation, the LLMOps path from Module 5's, and Agentic DevOps from Module 6's.
