Deep Dive — Under the Hood of the Lexicon

The lesson gave you plain-language definitions and the lab proved you can recognize each term in a real snippet. Part 2 goes underneath three of those definitions to the actual mechanism: what a token is at the character level, what "close together in meaning" literally means as arithmetic, and why a context window is a hard numeric budget rather than a vague notion of memory. None of this changes what you already know — it's the same ten words, with the machinery exposed.

Where this picks up

Every script on this page is plain Python 3 from the standard library — no packages, no venv, no network calls, nothing to configure. Run them from anywhere; re-running is always safe.

cd labs/m2

How the vocabulary connects​

The lesson's map showed five terms living inside the LLM, one pattern layered on top, and two terms belonging to the agent architecture. Here's the same map with the mechanism each term actually touches:

Parameters live one level up from everything else — they're baked into the network during training and don't move at inference time. Everything else on this page happens at inference, the moment you actually call the model.

1 — What a token actually is​

Analogy: a real tokenizer's vocabulary is a warehouse of tens of thousands of pre-cut building blocks, learned from data so that common chunks of text ("the", "-ing") get their own block, and rare or unfamiliar text gets built out of several smaller blocks stuck together. Text never ships as whole words — it ships as whichever blocks the warehouse has on the shelf.

The script below is a hand-written, 15-entry version of that idea — nowhere near a real tokenizer's ~100,000-entry vocabulary, but the matching rule is the same one real tokenizers use: scan left to right, and always take the longest chunk you have a block for before falling back to something smaller.

python3 tokenize_demo.py

Expected output

'the'                      -> ['the'] (1 token)
'jumping'                  -> ['jump', 'ing'] (2 tokens)
'uncharacteristically'     -> ['un', 'characte', 'ristic', 'ally'] (4 tokens)
'extraordinary'            -> ['extra', 'ordinar', 'y'] (3 tokens)

A common word like "the" is one block because it's common enough to earn its own entry. A word built from a common root plus a common suffix ("jumping") comes out as two. A rare, multi-part word ("uncharacteristically") gets chopped into several small pieces because nothing in the warehouse is big enough to cover it in one go. This is the actual reason token counts don't track word counts: jargon, product names, code identifiers, and non-English text all tend to hit more "unfamiliar, chop it up" cases than common English prose does — the same idea can cost noticeably more tokens depending only on how it's phrased.

2 — Embeddings are literally points in space​

Analogy: think of a city where every building sits at exact GPS coordinates, and buildings with a similar purpose end up clustered near each other — not because anyone planned it that way, but because that's how the city grew. An embedding is exactly that: a point with coordinates (just a lot more than two of them), placed so that similar meanings end up near each other and unrelated meanings end up far apart. "Similarity" isn't a judgment the model makes on the spot — it's a distance you can calculate.

The script below hand-picks four such points and calculates that distance the same way a real vector database does: cosine similarity, the angle between two vectors, not their raw distance apart.

python3 embeddings_demo.py

Expected output

Cosine similarity to 'cat' (1.0 = same direction, 0.0 = unrelated):

  cat vs kitten   1.000
  cat vs dog      0.642
  cat vs car      0.158

cat and kitten end up nearly identical in direction — a real embedding model would place those two close together for the same reason a thesaurus would. dog sits at a real but smaller angle: same general category (animal, pet), different word. car sits far off to the side, close to unrelated. This is the entire mechanism behind "customers who bought X also bought Y" and behind a RAG system finding the right paragraph even when you didn't type any of its exact words — it's a nearest-neighbor search over exactly this type of point cloud, at a scale of millions of points instead of four.

3 — The context window is a hard numeric budget, not memory​

Analogy: a context window behaves less like a filing cabinet — where things you put away stay retrievable forever — and more like a single desk. Everything the model needs for this one answer has to physically fit on that desk at the same time: your instructions, the conversation so far, anything retrieved. Once the desk is full, something has to come off before anything new goes on, and what comes off is usually the oldest material.

python3 context_budget.py

Expected output

Context window:      128,000 tokens
System prompt:            800 tokens
Conversation so far:   61,000 tokens
Retrieved documents:   34,000 tokens
Used so far:           95,800 tokens
Reserved for answer:    4,000 tokens
Headroom left:         28,200 tokens

This script adds up exactly what a real application has to account for before every call: a fixed system prompt, the running conversation, and whatever a RAG step retrieved for this turn — then subtracts a reserve for the answer itself. What most people don't realize until they hit it in production: a "bigger context window" release doesn't just mean more room, it also usually means slower and more expensive calls, because the model has to attend across every token in that window for every token it generates. Advertised window size and the size at which answer quality stays reliable are also not the same number — providers publish the first one, and you learn the second one by testing with content that actually matters to your use case.

Where you will use this
  • Token count depends on phrasing and language, not just word count. Use it when: you're estimating API cost for a feature that will handle jargon-heavy, code-heavy, or non-English input — budget from real sample text, not an English word-count guess.
  • "Similar" in a search or recommendation feature is a calculated distance, not a judgment call. Use it when: a RAG system returns an irrelevant chunk and you need to debug whether the problem is retrieval (wrong points came back) or generation (right points came back, model wrote a bad answer from them) — these are different bugs with different fixes.
  • The context window is a shared budget, not free memory. Use it when: a chat feature or agent starts producing worse answers as a conversation grows — check what's actually occupying the window (history, retrieved docs, tool output) before assuming the model "got confused."
