Deep Dive — Streaming, a Tool Registry, and a Basic Eval

The lab wired an LLM, an agent loop, and RAG into one assistant and put it behind an endpoint that answers correctly and admits what it doesn't know. That's a working assistant. Part 2 covers three things that separate a working assistant from one you'd trust in someone else's hands: making the wait for an answer visible instead of silent, adding a fourth tool without a growing agent's tool list turning into two hand-synced lists that drift apart, and a small automated check that catches a regression before a real user does.

Where this picks up

This page reuses labs/m9/.venv and labs/m9/chroma_db/ exactly as the lab left them. If you're arriving fresh, or deleted chroma_db/ at the lab's teardown:

cd labs/m9
python3 -m venv .venv && source .venv/bin/activate && pip install -r requirements.txt
python3 rag_ingest.py

Safe to re-run even if you already did this in the lab — rag_ingest.py drops and recreates its collection every time. Nothing on this page needs the API server running; every script below calls the agent directly, in-process.

1 — Streaming: don't make the client wait for the whole answer​

Analogy: think about the difference between texting someone and watching the three dots that mean they're typing turn into words on your screen, versus sending a message and getting total silence until their entire reply lands at once, seconds later. Same final message either way — but the first one tells you something is happening, and the second one leaves you staring at a blank screen wondering if it worked at all.

Every LLM call in this course so far, including run_agent() in the lab, waited for the full response before printing anything. That's a fine choice for a tool-call turn — you genuinely need the whole tool_calls payload before you can execute anything — but it's a poor choice for the final answer a person is reading live, especially once retrieve_document or web_search results make that answer longer.

python3 stream_chat.py

Expected output — a live model call, so the exact wording and chunk count will vary run to run; what should stay the same in shape is more than one content chunk:

Prompt: In three short sentences, explain what a RAG pipeline is.

Streamed response:
A RAG (Retrieval Augmented Generation) pipeline enhances large language models by giving them access to external, up-to-date information. It first retrieves relevant documents or data from a knowledge base based on a user's query. This retrieved context is then used by the LLM to generate a more accurate and fact-based response, reducing hallucinations.

Received 2 content chunks totaling 355 characters.

stream_chat.py asks for stream=True on the same chat.completions.create() call you've used all course, and the response comes back as a sequence of small chunks instead of one block — each one printed the moment it arrives, instead of held until the whole answer is ready.

One nuance worth knowing before you wire this into the capstone's /ask endpoint: you can't stream a tool-calling turn the way run_agent() uses them, because the loop needs the complete tool_calls request — the tool name and every argument — before it can call anything. What you'd actually stream in a real version of this assistant is only the last turn, the one where the model has no more tool calls left and is producing the final answer for the client to read. Every earlier turn in the loop stays exactly as it is in agent.py today — request, wait, get the full response back, decide what to do next.

2 — A tool registry: adding a fourth tool without touching the loop​

Analogy: picture that helpdesk from the lesson growing past three specialists. Scribble each new hire's name and specialty on two separate boards — a call-routing list and a duty roster — and you're trusting two hand-maintained lists to always agree, forever, no matter who's adding the next name. Enter each specialist once into a shared staff directory that both boards read from, and there's only one place a name can go stale or get spelled two different ways.

tools.py's TOOLS list and TOOL_FUNCTIONS dict are exactly those two boards — every new tool needs a matching entry in both, spelled identically, and a mismatch between them is silent until the model actually tries to call the tool that isn't there.

python3 tool_registry.py

Expected output — the timestamp on the last line reflects when you ran it:

Registered 4 tools: web_search, calculator, retrieve_document, current_time
  calculator('6 * 7')          -> 42
  calculator is tools.calculator: True
  web_search is tools.web_search: True
  retrieve_document is tools.retrieve_document: True
  current_time()                -> 2026-08-14 23:47:49 UTC

tool_registry.py builds one dict, keyed by tool name, where each entry carries its schema and its function together — the staff directory. TOOLS and TOOL_FUNCTIONS become two one-line views generated from that dict, and the script proves the original three tools still work completely unchanged before adding a fourth, deliberately trivial one (current_time) to show what adding a tool actually costs once the registry exists: one function, one dict entry, nothing else.

agent.py's loop only ever consumed TOOLS and TOOL_FUNCTIONS — it never knew or cared whether those came from two hand-written lists or one generated registry. That's exactly why the registry is a safe change: it moves where the two structures come from, not what the loop does with them.

3 — A basic eval: catching a regression before a real user does​

Module 8's deep dive drew a line between a test suite (one fixed input, one fixed expected output, pass or fail) and an eval suite (graded against a rubric, because two correct answers can be worded differently). Module 7's eval_harness.py already put that idea to work on a regression model, checking Mean Absolute Error against a tolerance instead of one exact number. This section is the same idea, aimed at the assistant you just built instead of a model in the abstract.

python3 eval_assistant.py

Expected output — the calculator result and the pass/fail verdicts should be stable run to run; the RAG and out-of-scope answer wording (live model calls) will vary:

Running 3 eval cases against the capstone assistant

  -> calling calculator({'expression': '12 * 8'})
     result: 96
[PASS] calculator arithmetic
       why this check: 12 * 8 = 96 is deterministic — the tool either got called correctly or it didn't.
       answer preview: 96

  -> calling retrieve_document({'question': 'how many vacation days do employees get per year?'})
     result: mployees accrue 22 days of paid vacation per year, credited monthly at a rate of a little under 2
days per month. Unused vacation days may be carried over into the next calendar year, up to a maximum

[PASS] RAG-answerable question
       why this check: a real answer came back — not empty, not a crash. The exact wording is expected to vary run to run.
       answer preview: Employees accrue 22 days of paid vacation per year.

  -> calling retrieve_document({'question': "company's parental leave policy"})
     result: mployees accrue 22 days of paid vacation per year, credited monthly at a rate of a little under 2
days per month. Unused vacation days may be carried over into the next calendar year, up to a maximum

[PASS] honest out-of-scope question
       why this check: the document doesn't cover this — the assistant should say so rather than crash or return nothing. Read the printed answer below to confirm it actually declined instead of guessing.
       answer preview: I'm sorry, but the document does not contain information about the company's parental leave policy.

EVAL PASSED — all cases landed in the expected shape.

eval_assistant.py runs three fixed questions straight through run_agent() — no server, no curl, the same in-process technique eval_harness.py used against Module 7's API. Each case checks a shape, not exact wording: the calculator question checks that 96 appears in the answer, because 12 * 8 is deterministic and either the tool ran correctly or it didn't; the RAG and out-of-scope questions check that a real, non-empty answer came back with no raw stack trace in it, because the actual phrasing is expected to vary run to run the same way it did between your two agent.py runs in the lab.

Run this before you ship a change to the system prompt, swap which provider LLM_MODEL points at, or edit a tool's implementation — the same discipline as running a test suite before a merge, aimed at an agent instead of a function.

Where you will use this
  • A streamed response shows a client something is happening the moment the model starts answering, instead of a silent multi-second wait while tool calls and generation finish behind the scenes. Use it when: you're building a chat UI or CLI on top of this /ask endpoint and the agent's tool calls add real latency — stream only the final, no-more-tool-calls turn, never the intermediate reasoning and tool-call turns in between.
  • A tool registry turns "add a tool" into one new entry instead of two hand-synced lists, and removes a silent name collision as a failure mode. Use it when: more than one person is adding tools to the same agent, or you're past three or four tools and keeping a schema list and a function dict in sync by hand is starting to slip.
  • A shape check — the right number showed up, the answer is non-empty, no stack trace leaked through — survives normal wording variation between runs the way an exact-string check never would. Use it when: you're deciding what an automated check should assert about an LLM-backed feature's output — assert the property that has to be true, not the exact sentence.
  • Running the eval before a prompt, tool, or provider change catches a regression before a real user asking a real question does. Use it when: you're about to edit a system prompt or swap a model on an agent that's already answering questions for someone other than you.

Teardown​

Nothing new was seeded on this page beyond three script runs — no server started, no files written beyond what chroma_db/ already had from the lab. If you're moving on to Module 10, leave labs/m9/.venv and labs/m9/chroma_db/ as they are; nothing here needs any other cleanup.
