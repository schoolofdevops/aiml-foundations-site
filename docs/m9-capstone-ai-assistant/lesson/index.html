Capstone — Your AI Assistant, End to End

What happens when five separate things become one thing?​

You've built five separate pieces across this course. A three-line call to an LLM in Module 1 and Module 5. An agent that reasons over tools in Module 6. A RAG pipeline that answers from your own PDF, also in Module 6. A model served behind a real API in Module 7 and Module 8. Each one worked on its own, in its own lab, torn down when you were done.

Today you stop tearing them down. You wire the LLM call, the agent loop, and the RAG pipeline into one assistant, and you serve that assistant behind the same kind of API Module 7 taught you to build. By the end of this lesson you can describe that assistant's full architecture end to end, and you know exactly which of your earlier labs each piece of it comes from — nothing here is new machinery, only new wiring.

The capstone brief: what you're building​

Here's the plain description, before any code: a document-savvy AI assistant. You ask it a question. If the question needs something current, it searches the web. If it needs a calculation, it does the math instead of guessing. If it needs something from a PDF you gave it, it looks the answer up in that document instead of making one up. And it does all of this behind a single API endpoint, so anything — a script, a curl command, a real client — can ask it a question the same way you'd ask a colleague.

That's the whole brief. Nothing about it is a new idea. It's Module 6's agent loop, with a third tool added, standing behind Module 7's serving pattern.

The architecture, end to end​

This is the diagram this whole course has been building toward — every earlier module is one box in it.

Read it left to right. A request lands on the /ask endpoint — the same shape as Module 7's /predict, only asking a question instead of handing over a set of features. The endpoint hands the question to the agent loop from Module 6, unchanged. The loop reasons, and if it needs something it doesn't already know, it picks one of three tools: search the web, do a calculation, or look inside the PDF you gave it. The tool's result goes back into the loop, the model reasons again, and once it has enough, it answers — and that answer is what the endpoint sends back to whoever asked.

The project spine, converged — and what didn't converge​

It's worth being precise about what "capstone" means here, because not everything you built folds into this one assistant. Module 3's regression model predicted a house price. Module 4's neural net classified a handwritten digit. Both were real, standalone labs, and neither one is part of a document-savvy assistant — a predictor and a classifier don't belong inside a chat loop, and forcing them in would be a fake connection, not a real one.

What does converge here is the generative and agentic thread: the LLM call from Module 1 and Module 5, the agent loop and RAG pipeline from Module 6, and the serving pattern from Module 7 and Module 8. Four separate labs, one assistant. That's an honest, satisfying convergence on its own — you don't need the whole course to fold into one artifact for today to be the payoff module.

Three tools, one assistant​

Analogy: think about a good helpdesk. Ask it something written in the company manual, and it opens the manual and reads you the relevant page — it doesn't recite the answer from memory, because memory drifts and the manual doesn't. Ask it something the manual can't possibly cover, like today's exchange rate, and it looks it up instead of guessing. Ask it to work out a number, and it reaches for a calculator instead of doing arithmetic in its head under pressure. A good helpdesk doesn't try to answer everything the same way — it picks the right method for the question in front of it.

That's your assistant's three tools. calculator is the arithmetic you already trust from Module 6, unchanged. web_search is the same free, no-key web search from Module 6, unchanged. The new one is retrieve_document — Module 6's bonus RAG pipeline, which used to be a script you ran by hand after deciding the question was about the PDF, now turned into a tool the agent decides to call for itself. The agent loop doesn't change at all to support this. It already knew how to pick a tool from a list and read back whatever came out. Handing it a third option is exactly as much new code as handing it a second one was in Module 6 — one more schema, one more Python function, nothing structural.

Honesty over confidence​

Here's where today's lab deliberately tries to break the assistant, not just show it working. Module 5 taught you why LLMs hallucinate: a model always produces its most likely next words, whether or not those words are actually true. Module 6 taught you prompt injection: text a tool returns can carry instructions the model shouldn't trust. Today's assistant sits at the intersection of both risks, because retrieve_document hands the model real text pulled from a document it didn't write.

The defense you'll test in the lab is a plain instruction in the system prompt: if the retrieved passages don't answer the question, say so, instead of falling back on a plausible-sounding guess. You'll ask your assistant something the PDF genuinely doesn't cover, and a working assistant tells you it doesn't know. That's not a failure case to patch around — it's the one honest answer to a question the document can't answer, and it's the single most convincing thing you can show someone when you demo this. A confident wrong answer is worse than an honest "I don't know," every time.

What's next​

You now have the full picture: what you're building, why each piece is in it, and which labs — not new material — supplied every piece. The lab is where you actually wire it together, run it, break it on purpose, and watch the honest failure happen live. Module 10 is graduation: a recap of everything you've built, a final practice test, and the three paths — MLOps, LLMOps, and Agentic DevOps — that pick up from exactly where this assistant leaves off.
