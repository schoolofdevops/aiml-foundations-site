Lab — Build Your Capstone AI Assistant

Goal: Wire an LLM call, an agent loop with tools, and a RAG pipeline into one assistant, then serve it behind a single /ask endpoint. Run it, break it on purpose, and watch it handle a question it genuinely can't answer — honestly, instead of guessing.

Time: ~45 minutes Prerequisites: Module 6's lab, completed at least once (this lab reuses its agent loop and RAG pipeline directly), and a Google Gemini free-tier key from Module 1 Step 3 Option B — see Step 2 below.

Step 1 — Create this module's venv​

Every module's lab lives in its own folder with its own dependencies, and the capstone is no exception — even though nothing here is new code, it gets its own environment. From the root of the course repo (where you cloned aiml-foundations-labs):

cd labs/m9
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

Expected output

Using cached ...
Installing collected packages: pypika, flatbuffers, durationpy, brotli, websockets, ...
  openai, kubernetes, jsonschema, huggingface-hub, fastapi, tokenizers, ddgs, chromadb

Successfully installed ... chromadb-1.5.9 ... ddgs-9.14.4 ... fastapi-0.141.1 ...
  openai-3.0.0 ... pypdf-6.16.1 ... uvicorn-0.52.3 ... httpx-0.28.1 ...

Exact versions and the full package list will differ on your machine and over time — pip resolves whatever is current when you run it. What matters is that it ends with Successfully installed and no error.

requirements.txt is the union of what you've already installed twice before: openai, ddgs, chromadb, and pypdf from Module 6, plus fastapi, uvicorn, and httpx from Module 7/8. Nothing on this list is new to you — you're combining, not learning new packages.

Step 2 — Configure a provider that calls tools reliably​

Same reasoning as Module 6: small local models call tools unreliably, and today's assistant leans on tool calls more than any lab before it — three tools instead of two, chained together in a single answer. Recommended for this lab: Google Gemini's free tier. If you already set it up, reuse it in this new terminal:

source ../m1/.env

If you skipped it earlier, see Module 1 Step 3 Option B or Module 6 Step 2 for how to get a free key and set LLM_BASE_URL / LLM_API_KEY / LLM_MODEL. The code below is identical either way — only those three environment variables change.

Part 1 — Wire the Brain​

This part builds the assistant's reasoning: an LLM with tools, running the loop from Module 6. No new mechanism — you're assembling what you already validated.

Step 3 — Look at the two tools you already trust​

Open tools.py:

cat tools.py

The first two tools, web_search and calculator, are Module 6's tools.py, byte for byte unchanged — same ddgs-based search, same ast-based safe expression evaluator, never a raw eval() on model-provided text. If you want to re-confirm that yourself:

grep -n "ast.parse" tools.py

Expected output

54:        parsed = ast.parse(expression, mode="eval").body

You should see the same ast.parse(expression, mode="eval").body line Module 6 showed you. Skip past the third tool for now — retrieve_document — you'll come back to it in Part 2.

Step 4 — Run the agent before it has any documents​

agent.py is Module 6's agent loop, unchanged in shape, now importing three tools instead of two. Run it before you've given it anything to read:

python3 agent.py

Expected output — a live web search and a live model, so the exact wording (the news headline, the phrasing of the final answer) will differ on your run. What should stay the same in shape: retrieve_document returns a plain-text "no ingested document found" error, and the final answer states that plainly instead of guessing a number.

Task: First, tell me how many vacation days employees get per year, according to the document you have access to. Then search the web for one current AI news headline. Finally, use the calculator tool to work out 15% of 200. Answer all three parts, clearly labeled.

  -> calling retrieve_document({'question': 'how many vacation days employees get per year'})
     result: Error: no ingested document found (Collection [m9_capstone_demo] does not exist). Run rag_ingest.py first.
  -> calling web_search({'max_results': 1, 'query': 'current AI news headline'})
     result: 1. Google News - Overview — ABC News - Breaking News, Latest News and Videos.AI safety warnings mount as frontier models test new limits. (https://news.google.com/stories/...)
  -> calling calculator({'expression': '0.15 * 200'})
     result: 30.0

Final answer:
Here are the answers to your requests:

**Vacation Days:** I was unable to retrieve information about vacation days from the document as no document was found.

**Current AI News Headline:** AI safety warnings mount as frontier models test new limits.

**15% of 200:** 30.0

Watch what happens on the part of the task that asks about the document. The model calls retrieve_document, and because you haven't run rag_ingest.py yet, that tool returns a plain-text error — "no ingested document found" — instead of crashing. A model following the system prompt should tell you plainly that it doesn't have that information yet, rather than inventing a vacation-days number from thin air. That's the honest-failure behavior working correctly, on the tool that has nothing to work with — the same behavior you'll test more deliberately once it does have something to work with.

Part 2 — Give It Knowledge & Hands​

This part gives the assistant something to actually retrieve from, then puts the whole thing behind an API.

Step 5 — Look at the third tool: retrieve_document​

Open tools.py again and find retrieve_document:

file: labs/m9/tools.py

def retrieve_document(question: str) -> str:
    try:
        client = chromadb.PersistentClient(path=CHROMA_PATH)
        collection = client.get_collection(COLLECTION_NAME)
    except Exception as exc:
        return f"Error: no ingested document found ({exc}). Run rag_ingest.py first."

    try:
        question_embedding = _embed(question)
        results = collection.query(query_embeddings=[question_embedding], n_results=TOP_K)
    except Exception as exc:
        return f"Error: retrieval failed ({exc})"

    chunks = results["documents"][0]
    if not chunks:
        return "No relevant passages found in the ingested document."
    return "\n\n---\n\n".join(chunks)

This is Module 6's bonus RAG lab — rag_query.py's embed-then-retrieve logic — with one real change: it used to be a script you ran by hand, after you'd already decided the question was about the PDF. Now it's a tool, with a schema right below it in the same file, and the agent decides for itself whether a question needs it. That's the only new idea in this whole capstone — everything else is reuse.

retrieve_document has nothing to search until you run the ingest step — same script, same shape as Module 6's bonus lab:

Step 8 — Serve it behind FastAPI​

api.py wraps agent.py's run_agent() behind a single endpoint, in Module 7 and Module 8's exact FastAPI pattern:

file: labs/m9/api.py

@app.post("/ask", response_model=AskResponse)
def ask(request: AskRequest):
    answer = run_agent(request.question)
    return AskResponse(answer=answer)

Notice this is def ask(...), not async def ask(...). FastAPI runs a plain def route in a worker thread pool automatically, so one slow agent loop — several tool calls and LLM round trips, easily a few seconds — doesn't block every other request that hits this server while it waits. Writing async def here and calling the blocking OpenAI client directly inside it would do exactly that; see Common Pitfalls below.

Start the server:

uvicorn api:app --reload

Expected output

INFO:     Started server process [87839]
INFO:     Waiting for application startup.
INFO:     Application startup complete.
INFO:     Uvicorn running on http://127.0.0.1:8000 (Press CTRL+C to quit)

The process ID on the first line and the --reload watcher lines (if your terminal shows them) will differ every run — what matters is the Application startup complete and Uvicorn running lines. Leave this running. Open a second terminal for everything from here on — the server needs this one to itself.

Demo Day​

Time to run it for real, and to break it on purpose. From your second terminal, in labs/m9:

A question the document can answer:

curl -X POST http://127.0.0.1:8000/ask \
  -H "Content-Type: application/json" \
  -d '{"question": "How many vacation days do employees get per year?"}'

Expected output — a live model call, so exact wording will vary run to run; the number, grounded in the ingested PDF, should not:

{"answer":"Full-time employees accrue 22 days of paid vacation per year."}

A question the document cannot answer — this is the deliberate break. The sample handbook never mentions parental leave:

curl -X POST http://127.0.0.1:8000/ask \
  -H "Content-Type: application/json" \
  -d '{"question": "According to the document, what is the company'"'"'s parental leave policy?"}'

Expected output — again wording will vary run to run; the assistant should decline rather than invent a policy:

{"answer":"I am sorry, but the document does not contain information about the company's parental leave policy."}

A working assistant tells you it doesn't know, rather than inventing a policy that sounds plausible. This is Module 5's hallucination risk and Module 6's honest-RAG system prompt, proven end to end, behind a real HTTP endpoint instead of a script you ran locally.

A question that needs more than one tool at once:

curl -X POST http://127.0.0.1:8000/ask \
  -H "Content-Type: application/json" \
  -d '{"question": "Search for one current AI news headline, then tell me what 20% of 350 is."}'

Expected output — the headline text will vary (live web search); the arithmetic should not:

{"answer":"Here's a current AI news headline: \"AI News & Artificial Intelligence | TechCrunch\".\n\n20% of 350 is 70.0."}

You now have a working, document-savvy AI assistant that reasons over tools and answers from your own data, behind one API call. That is genuinely worth a screenshot — the request, the honest "I don't know" on the parental-leave question, and a correct answer on the others, side by side. If you've been sharing progress through this course, this is the natural moment to post that result.

Stretch goals​

Optional. None of these are required to complete the module — pick one if you want to keep building.

  • Add a fourth real tool — a unit converter, a ticket lookup, anything your assistant doesn't already do. The Deep Dive's tool-registry pattern shows you how to add it without touching the agent loop.
  • Swap the vector store — point retrieve_document at a different local vector database instead of Chroma; the interface (embed, query, get back the closest chunks) stays the same no matter which one is underneath.
  • Add conversation memory across turns — right now every /ask call starts a fresh conversation. Carry the message list between requests (keyed by a session ID) so the assistant remembers what you asked it a minute ago.

Common Pitfalls​

Tool-name collision — two tools registered under the same name

Every tool needs a name that matches in three places: the "name" field inside its schema in TOOLS, and the key it's registered under in TOOL_FUNCTIONS. Copy-pasting an existing tool as a starting point for a new one is the easiest way to end up with two entries named retrieve_document — the second one silently overwrites the first in TOOL_FUNCTIONS, and the model has no way to tell the difference from the schema alone. Give every new tool a name you've grepped for first.

Answers about the document sound stale, or claim the document doesn't cover something it actually does

Almost always means rag_ingest.py was run against a different PDF than the one you're now asking about, or wasn't re-run after you edited the PDF. retrieve_document only ever reads whatever is currently in chroma_db/ — it has no way to know the file on disk changed underneath it. Re-run python3 rag_ingest.py against the PDF you actually want answers from, every time that PDF changes.

Converting /ask to async def without an async LLM client

If you "helpfully" rewrite ask() in api.py to async def ask(...) but still call the regular, blocking OpenAI client inside it, you've made things worse, not better — a blocking call inside an async def route runs directly on the single event loop every request shares, so one slow agent loop now stalls every other request on the server, not just its own. The lab's def ask(...) (a plain, synchronous function) is correct as written, because FastAPI puts plain def routes in a worker thread pool automatically. If you do want a true async version, you'd need the OpenAI client's async variant (AsyncOpenAI) throughout — a bigger change than it looks, and out of scope for this lab.

The agent never calls a tool, or claims it did without a trace line for it

Same reliability gap Module 6 warned you about — you're most likely on the Ollama path with a small local model. Switch to the Gemini path from Step 2 and re-run.

json.decoder.JSONDecodeError printed inline, not a crash

agent.py catches malformed tool-call JSON the same way Module 6's did — you'll see a called with malformed JSON arguments line, not a stack trace, and the loop continues. Rare, and not something you need to force.

Provider errors — AuthenticationError, Connection refused, model not found

Same causes and fixes as Module 1 and Module 6's Common Pitfalls — a missing or unsourced .env, or Ollama not running. See either module's Common Pitfalls section for the exact fix for each.

Teardown​

Stop the server with Ctrl+C in the terminal running uvicorn, then:

deactivate

chroma_db/ is a local folder you can delete any time with rm -rf chroma_db — it regenerates in full the next time you run rag_ingest.py. There are no containers and no cloud resources to clean up. If you're moving straight on to the Deep Dive, leave labs/m9/.venv as it is — it reuses this exact environment.
